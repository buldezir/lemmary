# Самостоятельный хостинг с Docker {#self-hosting-with-docker}

В опубликованном образе есть всё, что нужно Lemmary: бинарный файл Go, собранное SPA
и эта документация, poppler для работы с PDF и сборка FAISS, с которой линкуется
векторный поиск. На хосте не нужно устанавливать ничего, кроме Docker.

Чтобы запускать из исходников, см. [Среда разработки](/ru/development).

## Быстрый старт {#quick-start}

```bash
cp .env.example .env
# Optional: put an AI key in .env so the first boot skips the wizard.
docker compose up -d
```

Откройте [http://127.0.0.1:8090](http://127.0.0.1:8090). На свежем томе встроенный
[мастер настройки](/ru/setup#first-launch-setup-wizard) создаёт учётную запись
администратора и запрашивает ключи для OCR и языковой модели; одного ключа Mistral
хватает на то и другое. Что указать в `.env`, см. в разделе
[AI-провайдеры](/ru/ai_providers).

`docker-compose.yml` намеренно короткий:

```yaml
services:
  app:
    image: ghcr.io/buldezir/lemmary:latest
    restart: unless-stopped
    env_file: [.env]
    ports: ["8090:${PORT:-80}"]
    volumes: [app_data:/app/pb_data]
```

Добавьте `--build`, чтобы собрать образ локально из `Dockerfile`, а не скачивать
его. Публикуемые теги — `latest` (ветка по умолчанию), версия релиза (`1.2.3`, `1.2`,
`1`) и sha коммита, для `linux/amd64` и `linux/arm64`.

## Что где хранится {#what-lives-where}

Краткий обзор архитектуры, включая хранение документов в S3 и место хранения
векторов эмбеддингов, см. в разделе [Хранение данных](/ru/storage).

При локальном файловом хранилище по умолчанию всё состояние находится в
`/app/pb_data` на томе `app_data`:

| Путь | Содержимое |
| --- | --- |
| `data.db` | документы, метаданные, настройки, чаты — включая OCR-текст, хранящийся прямо в строках |
| `storage/` | загруженные исходные файлы и сгенерированные миниатюры |
| `bleve/documents`, `bleve/chunks` | [поисковые индексы](/ru/setup#full-text-search) — производные данные, при удалении перестраиваются при следующей загрузке |

Оценивая размер тома, учитывайте не только файлы, но и базу данных: извлечённый
текст хранится в строке, а эмбеддинги добавляют примерно 30–60 КБ на документ.

Контейнер запускается от root лишь на время, необходимое, чтобы принять том,
созданный старым образом, работавшим от root, а затем окончательно переходит к
непривилегированному пользователю `app` (uid/gid 1000): он рендерит недоверенные PDF
через poppler, и эксплойт там не должен получить права root.

## Порты и обратные прокси {#ports-and-reverse-proxies}

Сервер слушает на `$PORT` (80 в образе), а compose-файл публикует его на `8090`.
Healthcheck образа опрашивает `/api/health` с щедрым стартовым периодом в 120
секунд, потому что при первой загрузке выполняются миграции и может перестраиваться
поисковый индекс по уже большому архиву.

Необязательная наблюдаемость — это второй порт. Задайте
[`METRICS_ADDR`](/ru/setup#always-env-backed), чтобы отдавать эндпоинт для сбора
метрик Prometheus; если переменная не задана, он выключен. Голый порт (`9464`)
слушает на всех интерфейсах внутри контейнера — именно это нужно для опубликованного
порта или сбора метрик из сети compose. Сопоставления порта намеренно нет в
`docker-compose.yml`: у эндпоинта нет аутентификации, и он не должен становиться
доступным из интернета из-за того, что задана переменная. Укажите хост
(`127.0.0.1:9464`), чтобы оставить его на loopback при запуске бинарного файла на
хосте.

SPA обращается к тому источнику, с которого оно было загружено, поэтому **для
контейнера не нужно настраивать никакой URL**: `VITE_POCKETBASE_URL` в `.env` влияет
только на фронтенд, собранный из исходников. Поставьте перед ним прокси,
терминирующий TLS, и две вещи стоит задать явно:

- [`PASSKEY_RP_ID` и `PASSKEY_ORIGINS`](/ru/setup#always-env-backed), если прокси не
  передаёт исходный `Host` или `X-Forwarded-Proto`. Каждый зарегистрированный ключ
  доступа привязан к `PASSKEY_RP_ID`, поэтому его последующее изменение делает все
  ключи непригодными.
- `IMPORT_ALLOW_PRIVATE=1`, если вы импортируете из экземпляра Paperless-ngx в той же
  локальной сети или сети Docker. Адреса облачных метаданных в любом случае остаются
  заблокированными.

### Traefik {#traefik}

Это оверлей, поэтому базовый файл остаётся пригодным и сам по себе:

```yaml
# docker-compose.traefik.yml
#   docker compose -f docker-compose.yml -f docker-compose.traefik.yml up -d
services:
  app:
    # Traefik reaches the container over the shared network, so nothing needs
    # publishing on the host any more. (!override replaces the base list.)
    ports: !override []
    networks: [proxy]
    labels:
      traefik.enable: "true"
      # Which network to dial when the container is on more than one.
      traefik.docker.network: proxy
      traefik.http.routers.lemmary.rule: "Host(`archive.example.com`)"
      traefik.http.routers.lemmary.entrypoints: websecure
      traefik.http.routers.lemmary.tls.certresolver: letsencrypt
      # The port inside the container, not the 8090 the base file published.
      traefik.http.services.lemmary.loadbalancer.server.port: "${PORT:-80}"

networks:
  proxy:
    external: true
```

Предполагается, что Traefik уже запущен с точкой входа `websecure`, резолвером
сертификатов `letsencrypt` и провайдером Docker во внешней сети с именем `proxy`.

Три вещи, которые эта конфигурация делает правильно без настройки и каждую из
которых другой прокси может сделать неправильно:

- **Ключам доступа не нужны переменные.** Traefik передаёт исходный `Host` и
  выставляет `X-Forwarded-Proto` — ровно то, из чего `PASSKEY_RP_ID` и
  `PASSKEY_ORIGINS` выводятся, когда не заданы.
- **Прокси не ограничивает загрузки.** По умолчанию Traefik не буферизует тело
  запроса, поэтому проходят и документ на 47 МБ, и подготавливаемый к импорту архив
  размером в гигабайты — никакого `client_max_body_size` увеличивать не нужно. Если
  вы добавляете middleware `buffering`, задайте его `maxRequestBodyBytes` больше
  `IMPORT_STAGING_MAX_BYTES`, иначе загрузка архивов начнёт завершаться ошибкой.
- **Deep Research продолжает стримить.** `POST /api/app/search/stream` — это
  server-sent events, а Traefik передаёт ответы потоком, а не буферизует их, поэтому
  каждый поиск, чтение и обзор по-прежнему появляются по мере выполнения. Не ставьте
  перед ним middleware `compress`, не исключив `text/event-stream`, иначе шаги
  придут одним куском в конце.
- **Длинным ответам нужен запас.** Исследование — это минуты работы, и поток каждые
  15 секунд отправляет кадр-комментарий, чтобы соединение никогда не простаивало.
  Это удовлетворяет `idleTimeout`, но **не** `respondingTimeouts.writeTimeout`: как и
  `http.Server.WriteTimeout` в Go, это абсолютный срок от начала ответа, и никакие
  heartbeat-сообщения его не продлевают. Оставьте его равным 0 на точке входа,
  которая обслуживает приложение, или задайте больше самого долгого ожидаемого
  прогона. `forwardingTimeouts.responseHeaderTimeout` важен по той же причине — он
  ограничивает ожидание первого байта от бэкенда. Потеря соединения больше не
  приводит к потере ответа (прогон в любом случае завершается, и реплика
  сохраняется), но пользователь, который за ним наблюдает, теряет отображение хода
  выполнения.

С [шифрованием хранимых данных](/ru/encryption) добавьте
`VAULT_ALLOW_INSECURE_GATE=1`: шлюз разблокировки отклоняет адрес привязки, отличный
от loopback, а внутри контейнера приложение привязывается к `0.0.0.0` независимо от
того, опубликован порт или доступен только из Traefik, — изнутри оно не может
отличить одно от другого. TLS тогда заканчивается на Traefik, поэтому пароль
разблокировки проходит по сети Docker открытым текстом. Это другой компромисс, чем
публикация на loopback, которую делает `docker-compose.encrypted.yml`, и на него
стоит идти осознанно.

## Повседневная работа {#day-to-day}

```bash
# Create or reset the admin account (never resets a password that exists)
docker compose exec -u app app /app/lemmary superuser upsert admin@example.com 'your-password'

# Logs; LOG_LEVEL=info in .env turns on JSON slog on stdout
docker compose logs -f app

# Upgrade
docker compose pull && docker compose up -d
```

Миграции выполняются при запуске, поэтому обновление — это pull и перезапуск. Явные
аргументы передаются бинарному файлу без изменений, благодаря чему работают `exec` и
`docker compose run --rm app <subcommand>`.

## Резервные копии {#backups}

Их два вида, и они отвечают на разные вопросы:

- **Экспорт из приложения** — любой вошедший пользователь скачивает собственную
  библиотеку одним zip-архивом (файлы, OCR-текст, метаданные, миниатюры, таксономия)
  и восстанавливает её в этот или другой экземпляр. Архив не содержит ни настроек, ни
  API-ключей. См. [Резервное копирование и восстановление](/ru/setup#backup-and-restore).
- **Снимок тома** — весь экземпляр, включая настройки и ключи. Сначала остановите
  контейнер, чтобы SQLite не копировалась посреди записи:

  ```bash
  docker compose stop
  docker run --rm -v lemmary_app_data:/v -v "$PWD:/out" alpine \
    tar czf /out/lemmary-pb_data.tar.gz -C /v .
  docker compose start
  ```

## Ресурсы {#resources}

В образе закреплены `OPENBLAS_NUM_THREADS=1` и `OMP_NUM_THREADS=1`: OpenBLAS и OpenMP
по умолчанию запускают по потоку на ядро внутри процесса, который и так
параллельно обслуживает запросы, а по одному потоку на каждую библиотеку не даёт
векторному поиску остановить остальную часть сервера на маленькой машине.

## Локальный OCR {#local-ocr}

По умолчанию OCR — это облачный API, то есть каждый скан загружается кому-то
другому. Второй оверлей размещает OCR-движок на этом же хосте — контейнер-сайдкар
без опубликованного порта и без API-ключа:

```bash
docker compose -f docker-compose.yml -f docker-compose.local-ocr.yml \
  --profile docling up -d
```

Затем задайте `OCR_SDK=docling` в `.env` на свежем томе или добавьте провайдер
Docling в **Настройки → Провайдеры** на уже загружавшемся экземпляре. Это не
бесплатно: образ на несколько гигабайт, несколько гигабайт оперативной памяти и
секунды на страницу вместо миллисекунд. Сначала прочитайте
[Локальный OCR](/ru/local_ocr), особенно про таймаут, который нужно увеличить.

## Шифрование хранимых данных {#encryption-at-rest}

`VAULT_ENABLED=1` делает так, что на томе хранится только шифротекст, а экземпляр
запускается заблокированным. Для этого нужен рабочий каталог в памяти, который
приложение не может организовать само, и его предоставляет оверлей:

```bash
docker compose -f docker-compose.yml -f docker-compose.encrypted.yml up -d
```

Оверлей также задаёт размер tmpfs, отключает своп контейнера и заново публикует порт
только на loopback. Прежде чем включать шифрование, прочитайте
[Шифрование хранимых данных](/ru/encryption): потеря паролей всех учётных записей *и*
кода восстановления означает потерю архива, и обхода для оператора нет.

## Локальные эмбеддинги {#local-embeddings}

Deep Research умеет находить документы по смыслу, а не только по ключевым словам, и
для этого нужна модель эмбеддингов. Ещё два оверлея запускают её на этом хосте,
вместо того чтобы отправлять каждый фрагмент каждого документа облачному провайдеру:

```bash
# CPU, runs anywhere
docker compose -f docker-compose.yml -f docker-compose.embeddings.yml up -d

# NVIDIA GPU -- instead of the CPU file, not alongside it
docker compose -f docker-compose.yml -f docker-compose.embeddings-gpu.yml up -d
```

Они добавляют сайдкар без опубликованного порта и привязывают его, больше ничего не
меняя: OCR, извлечение и чат остаются там, где были. Оверлеи комбинируются, поэтому
шифрование и локальные эмбеддинги можно использовать вместе:

```bash
docker compose -f docker-compose.yml \
               -f docker-compose.encrypted.yml \
               -f docker-compose.embeddings.yml up -d
```

Помимо векторов, заложите ресурсы на саму модель — ~2,2 ГБ весов для модели по
умолчанию `BAAI/bge-m3` — и учтите, что при включённом хранилище сами векторы находятся в
tmpfs. См. [Эмбеддинги на собственном
оборудовании](/ru/local_embeddings).
