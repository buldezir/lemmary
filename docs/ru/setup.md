# Руководство по настройке {#configuration-guide}

Конфигурация времени выполнения, выбор при первом запуске и то, как ведут себя
функции Lemmary. Для обычного способа установки начните с раздела
[Самостоятельный хостинг с Docker](/ru/self_hosting). Инструменты для хоста и сборка
из исходников описаны отдельно в разделе [Среда разработки](/ru/development).

У двух областей есть собственные руководства:

- [AI-провайдеры и модели](/ru/ai_providers) — какого провайдера выбрать, блок
  `AI_*` / `OCR_*` и сколько стоят эмбеддинги
- [Совместимость с API Paperless-ngx](/ru/paperless_ngx) — совместимая поверхность
  `/api/`, подключение сторонних клиентов и импорт существующей библиотеки

## Переменные окружения {#environment-variables}

Все переменные задаются в `.env` в корне проекта (см. `.env.example`). Семейства
`AI_*` и `OCR_*` описаны в разделе
[AI-провайдеры и модели](/ru/ai_providers#the-provider-block).

`MANAGED` и переменные `LIMIT_*` существуют для облачных развёртываний и не
предназначены для самостоятельного хостинга; не задавайте их.

### Всегда из окружения {#always-env-backed}

| Переменная | По умолчанию | Описание |
| --- | --- | --- |
| `WORKER_CRON_EXPR` | `* * * * *` | Cron-выражение для обхода зависших ожидающих заданий (регистрируется один раз при запуске) |
| `LOG_LEVEL` | не задана (нет slog в stdout) | Минимальный уровень для строк JSON slog в stdout (`debug`, `info`, `warn`/`warning`, `error`). Игнорируется, пока включён `--dev` PocketBase (этот режим и так выводит всё в консоль, включая SQL). Таблицей логов по-прежнему управляет PocketBase Admin → Settings → Logs. |
| `METRICS_ADDR` | не задана (выкл.) | Адрес эндпоинта метрик OpenTelemetry, который отдаётся как цель сбора Prometheus на собственном порту, чтобы тому, кто собирает метрики, не требовались учётные данные для архива. Голый порт (`9464`) или порт без хоста (`:9464`) слушает на всех интерфейсах — это единственная форма, доступная в Docker через опубликованный порт &mdash; сопоставления намеренно нет в `docker-compose.yml`, поскольку эндпоинт без аутентификации не должен по умолчанию становиться доступным из интернета. Укажите хост (`127.0.0.1:9464`), чтобы оставить его на loopback при прямом запуске бинарного файла. Показывает частоту и задержку запросов по маршрутам, длительность заданий по исходу, глубину очереди ожидающих заданий, задержку исходящих вызовов AI/OCR по провайдеру и модели, число токенов, страницы, отправленные OCR-провайдеру, запуски Deep Search по режимам, сколько хранит экземпляр (документы, страницы, хранимые байты, учётные записи, а также самый большой хранимый файл в страницах и байтах) и метрики среды выполнения Go; никакого текста документов, имён учётных записей или путей. Хранимое представлено двумя датчиками под меткой `resource`: `lemmary_usage` для количеств и `lemmary_usage_bytes` для байтов. Стоит трёх запросов на каждый сбор: `COUNT` по `processing_jobs` плюс агрегат использования (одно index-only сканирование `documents` и `COUNT` по `users`). Если порт не удаётся занять, это пишется в лог, а приложение всё равно работает. |
| `MCP_ENABLED` | не задана (вкл.) | Задайте `0`/`false`/`no`/`off`, чтобы убрать эндпоинт [Model Context Protocol](/ru/mcp) только для чтения по адресу `POST /api/mcp` на порту приложения. По умолчанию он включён, потому что отвечает только на обычный bearer-токен и ничего не стоит, пока агент его не вызовет. Поисковые инструменты (`search_documents`, `read_documents`, `count_documents`) используют индекс Deep Search; инструменты простого доступа (`list_documents`, `get_document`, `list_taxonomy`) читают строки напрямую. Всё ограничено пользователем токена. Стоит одного запроса эмбеддинга на каждый поиск и на каждое чтение с `focus`, если эмбеддинги настроены; чтения возвращают выдержки из текста и никогда не вызывают языковую модель. Читается при запуске. |
| `IMPORT_ALLOW_PRIVATE` | не задана (заблокировано) | Задайте `1`/`true`, чтобы разрешить импорту из ngx обращаться к loopback и хостам RFC1918. Адреса link-local / облачных метаданных остаются заблокированными. Нужно, когда Paperless-ngx находится в той же локальной сети или сети Docker. |
| `UPLOAD_MAX_MB` | `100` | Ограничение на подготавливаемый PDF для разделения документа, в мегабайтах. Читается при запуске, а не из настроек: подготовка PDF требует памяти в несколько раз больше его размера, пока рендерятся страницы, поэтому это защищает хост не меньше, чем формирует продукт. Некорректное или неположительное значение заменяется значением по умолчанию, а не прерывает загрузку. Загрузка отдельных файлов ограничивается отдельно полем `documents.file` (47 МБ). |
| `INGEST_DIR` | не задана (выкл.) | Каталог внутри контейнера, отслеживаемый как папка приёма, см. [Папка приёма](#ingest-folder). Смонтируйте туда папку хоста (в `docker-compose.yml` эта строка есть в закомментированном виде). Читается при запуске; владелец, интервал сканирования и переключатель удаления после приёма находятся в Настройки → Приём. Стоит одного рекурсивного обхода каталога за интервал и одного чтения каждого нового файла; при выключенном удалении — одной небольшой строки в базе данных на каждый принятый файл. |
| `INGEST_IMAP_ENABLED` | не задана (выкл.) | Задайте `1`/`true`, чтобы читать почтовый ящик IMAP и превращать его вложения в документы, см. [Приём из IMAP](#ingest-from-imap). Читается при запуске; сервер, логин, папка и действие после импорта находятся в Настройки → Приём. Стоит одного входа в IMAP и одного поиска UID за интервал, одного запроса BODYSTRUCTURE на каждое новое письмо и скачивания каждого вложения, которое можно сохранить. Пароль почтового ящика хранится в `app_settings`, как и API-ключи провайдеров, и шифруется на диске только при `VAULT_ENABLED`. |
| `IMPORT_STAGING_MAX_BYTES` | `1073741824` (1 ГиБ) | Ограничение на архив, подготавливаемый к импорту (заказы Amazon, резервная копия Lemmary), в байтах. Подготовка нового архива отбрасывает предыдущий архив этой учётной записи, так что это ещё и объём диска, который одна учётная запись может занимать, пока решает, подтверждать ли импорт, — верхняя граница области подготовки примерно равна этому значению, умноженному на число учётных записей. Уменьшите его на маленьком томе; увеличьте для библиотеки, резервная копия которой больше гигабайта. Некорректное значение или значение меньше 1 МиБ заменяется значением по умолчанию, а не приводит к отклонению каждой загрузки. |
| `PASSKEY_RP_ID` | выводится из хоста запроса | Идентификатор проверяющей стороны для [входа по ключу доступа](/ru/passkeys): голое доменное имя без схемы и порта. По умолчанию — имя хоста, с которым пришёл запрос, и это правильно, если прокси передаёт публичный `Host`. Задайте его, если это не так, или чтобы закрепить родительский домен (`example.com` при обслуживании `app.example.com`). **Каждый зарегистрированный ключ доступа привязан к этому значению — его изменение делает все ключи непригодными.** Читается при запуске, а не из настроек. |
| `PASSKEY_ORIGINS` | выводится из схемы и хоста запроса | Разделённый запятыми список полных источников (схема, хост и порт), которым разрешено завершать церемонию ключа доступа. По умолчанию — источник, с которого пришёл запрос, со схемой из `X-Forwarded-Proto`, если заголовок есть. Задайте его, если приложение доступно более чем по одному источнику или если прокси, терминирующий TLS, не выставляет этот заголовок. |
| `VITE_POCKETBASE_URL` | `http://127.0.0.1:8090` | URL API PocketBase (фронтенд) |
| `SETUP_ADMIN_EMAIL` | — | Первая учётная запись администратора, создаваемая при первой загрузке, которая не находит ни одной. Создаёт запись `_superusers` **и** парную учётную запись `users`, в точности как мастер настройки. Никогда не сбрасывает уже существующий пароль. В сборке для разработки SPA также само входит с этой парой; production-бандл не содержит ни одного из значений. **Закомментирована в `.env.example`** — раскомментировав её в работающей установке, вы получили бы администратора, пароль которого опубликован в этом репозитории. |
| `SETUP_ADMIN_PASSWORD` | — | Её пароль, не короче 8 символов. Читается из `docker inspect` и `/proc/<pid>/environ` всё время жизни контейнера, поэтому это для локальных и CI-экземпляров — работающая установка должна использовать мастер или `superuser upsert`. |

## Мастер настройки при первом запуске {#first-launch-setup-wizard}

На свежей установке SPA жёстко блокируется, пока настройка не завершена:

1. **Создание администратора** — email и пароль. Создаёт учётную запись PocketBase `_superusers` **и** соответствующую учётную запись `users` (с теми же учётными данными), чтобы администратор мог владеть документами. Заменяет браузерный установщик PocketBase.
2. **Ключ доступа** *(необязательно)* — предложение добавить [ключ доступа](/ru/passkeys) для только что созданной учётной записи. Пропуск ничего не меняет, и предложение больше не появляется; ключ доступа можно добавить позже в **Ещё → Учётная запись**. Шаг скрыт на адресе, где ключ доступа создать нельзя (IP-адрес или обычный HTTP вне `localhost`).
3. **Провайдеры** — пошаговая форма из раздела [Пошаговая настройка AI-провайдеров](/ru/guided_ai_setup): ключ Mistral (OCR и эмбеддинги) и ещё один провайдер языковой модели, оба создаются одной отправкой формы. Любую половину можно оставить пустой; **Добавить провайдера вручную** переключает на форму по одному провайдеру за раз — это путь ко входу через ChatGPT, ключу `google_vision` или к `docling`/`local`, сайдкарам без ключей.
4. **Модели** — выбор провайдера и модели для OCR и Общего ИИ (всё, что делает языковая модель) и, при желании, для эмбеддингов. Если провайдеры пришли из пошаговой формы, все три поля заполнены заранее; для эмбеддингов можно выбрать **Нет**, и настройка завершится и без них.

Шаги 3 и 4 пропускаются, если в `.env` уже есть ключи — см.
[AI-провайдеры и модели](/ru/ai_providers). Администратор тоже может прийти из
окружения (`SETUP_ADMIN_EMAIL` / `SETUP_ADMIN_PASSWORD`, применяются при первой
загрузке, которая не находит ни одной учётной записи) или из CLI (`go run . superuser upsert EMAIL
PASS` из `backend/`, что также создаёт или обновляет парную учётную запись `users`).
При наличии и того и другого свежий том поднимается без единого вопроса. Пока ключей
нет, обычные пользователи видят экран «настройка не завершена»; завершить
конфигурацию может только администратор.

## Настройки (интерфейс администратора) {#settings-admin-ui}

1. Войдите с email и паролем **администратора** (при входе предпочитается учётная запись `users`; старые установки только с `_superusers` связываются автоматически через `/api/app/ensure-user`, который выставляет скрытый флаг `is_app_admin` у парной записи `users`).
2. Откройте **Настройки** в навигации (пункт показывается, когда `/api/app/me` сообщает `is_admin`). Там по одной вкладке на раздел, у каждой свой путь, и каждая сохраняет только свои поля: **Внешний вид** (`/settings`), **ИИ** (`/settings/ai`), **Обработка** (`/settings/processing`), **Воркер** (`/settings/worker`), **Дубликаты** (`/settings/duplicates`) и, если задана `INGEST_DIR` или `INGEST_IMAP_ENABLED`, **Приём** (`/settings/ingest`). На вкладке «ИИ» добавьте провайдеров, затем привяжите OCR, Общий ИИ и, при желании, Продвинутую модель к провайдеру и модели — см. [Привязка моделей в настройках](/ru/ai_providers#binding-models-in-settings). Изменения на лету перезагружают клиенты внутри процесса (без перезапуска).

`WORKER_CRON_EXPR` там не редактируется; измените `.env` и перезапустите или используйте PocketBase Admin → Settings → Crons.

**Дополнительные правила извлечения** (вкладка «Обработка») — единственная часть промпта извлечения, которую пишет администратор. Её содержимое добавляется к встроенному промпту после списка существующих корреспондентов и типов документов и перед правилами формата, поэтому там можно указать внутренние соглашения, которых фиксированный промпт знать не может, — «считать *Rechnung* типом документа Invoice», «помечать страховые документы тегом с номером полиса». Изменить набор сохраняемых полей они не могут: конвейер разбирает ответ в фиксированный набор, и промпт сообщает об этом после правил. До 4000 символов, по умолчанию пусто, применяется к документам, обработанным или обработанным заново после этого. Строка лога извлечения сообщает их длину как `rule_chars`, а запуск шага `extract_metadata` для каждого документа записывает промпт, с которым он фактически выполнялся (см. ниже).

`EXTRACTION_PROMPT_VERSION` там тоже не предлагается. Это чистый учёт — значение записывается в запуск шага `extract_metadata` каждого документа, чтобы метаданные можно было отследить до промпта, и никогда не попадает в сам промпт, — так что администратору настраивать нечего. Если заданы правила извлечения, этот запуск шага записывает `v1+rules.<digest>` вместо голой версии: правила меняют промпт, а версия — нет, и запуск, записанный просто как `v1`, указывал бы на промпт, которого больше не существует. Документы, извлечённые без правил, сохраняют голую версию, так что для экземпляра, где правила не заданы, ничего не меняется. `PATCH /api/app/settings` по-прежнему принимает `extraction_prompt_version`, и его можно изменить в PocketBase Admin → `app_settings`.

### Папка приёма {#ingest-folder}

Если задана `INGEST_DIR`, cron обходит этот каталог и превращает каждый файл, который можно сохранить (те же типы, что принимает загрузка: PDF, JPEG, PNG, WebP, TXT, CSV, DOCX, XLSX), в документ — в точности так, как если бы он был загружен: у файла вычисляется хеш, он проверяется по ограничению документа в 47 МБ и [потолку страниц](#the-page-ceiling) и ставится в очередь на полный конвейер. Обход рекурсивный (корень, который сам является символической ссылкой, отслеживается), а папки между корнем и файлом становятся его тегами — `Taxes/2024/invoice.pdf` приходит с тегами **Taxes** и **2024**; при этом повторно используется существующий тег, имя которого совпадает без учёта регистра, а несуществующие создаются. Извлечение добавляет к ним теги модели, а не заменяет их. Файлы и папки, начинающиеся с точки, символические ссылки, пустые файлы и всё, что нельзя сохранить, игнорируются; файл, изменённый за последние 30 секунд, ждёт следующего сканирования, чтобы не подхватить что-то недописанное.

Вкладка **Приём** (`/settings/ingest`) содержит три настройки (владелец и интервал общие с [приёмом из IMAP](#ingest-from-imap)):

- **Владелец** — учётная запись, которой принадлежит каждый документ из папки. По умолчанию — парная учётная запись `users` первого администратора; можно выбрать любую.
- **Сканировать каждые** — по умолчанию 5 минут. Сохранение перепланирует cron `dir_ingest` (виден в PocketBase Admin → Settings → Crons), так что изменение применяется без перезапуска. Принимаются минуты, на которые делится час (1–30), и часы, на которые делятся сутки (1–24); всё остальное отклоняется, поскольку шаг cron распределил бы запуски неравномерно.
- **Удалять исходный файл после приёма** — по умолчанию выключено. Если выключено, файлы остаются на месте и каждый импортируется один раз: журнал `ingest_files` учётной записи запоминает каждый принятый путь с его размером и временем изменения, так что ни перезапуск, ни удаление документа не возвращают файл; изменение файла импортирует его снова. Файл, содержимое которого уже есть в библиотеке, пропускается проверкой дубликатов по контрольной сумме. Файлы больше ограничения документа в 47 МБ и символические ссылки никогда не читаются. Если включено, файл удаляется, как только появляется его документ, и файл, оказавшийся дубликатом, тоже удаляется; при шифровании хранимых данных удаление ждёт, пока хранилище не запечатает документ, так что жёсткое завершение не может потерять обе копии. Файл, который конвейер отклоняет (содержимое не соответствует расширению, превышен потолок страниц), никогда не удаляется; это записывается в лог один раз, и файл пропускается.

### Приём из IMAP {#ingest-from-imap}

Если задана `INGEST_IMAP_ENABLED`, вкладка **Приём** предлагает также почтовый ящик, а cron (`imap_ingest`, с тем же интервалом, что и для папки) читает его папку: каждое вложение, имя которого имеет пригодное для хранения расширение выбранного типа, становится документом той же учётной записи, через те же хуки, что и загрузка. Тело письма никогда не становится документом, как и изображение где-либо внутри части `multipart/related` — логотипы и значки, которые HTML-тело встраивает через `cid:`, — если только отправитель не пометил его как `Content-Disposition: attachment`; изображение, отправленное настоящим вложением, по-прежнему учитывается. Встроенное изображение вне `multipart/related` импортируется, поскольку именно так iPhone Mail отправляет прикреплённые фотографии. Письма без таких вложений не затрагиваются. Если оставить сервер пустым, приём выключается.

Сканируется только почта, полученная после настройки почтового ящика: сохранение нового сервера, имени пользователя или папки запоминает этот момент (`imap_since`, показывается под полями «Почтовый ящик»), и всё, что уже лежало в папке, остаётся нетронутым, каким бы ни было действие после импорта. Новый пароль или новое действие после импорта сохраняют этот момент, так что ничего пришедшее тем временем не пропускается. Более старая почта — это догрузка: **Обслуживание → Почтовый ящик** принимает две даты включительно и импортирует вложения всего, что было получено между ними (IMAP `SINCE`/`BEFORE`, по дате получения на сервере). Догрузка открывает папку только для чтения, никогда не перемещает и не удаляет письма, не трогает журнал режима «Оставить» и полагается на проверку по контрольной сумме, чтобы пропускать вложения, уже имеющиеся в библиотеке, так что повторный запуск безвреден. Она выполняется в фоне и удерживает ту же блокировку, что и запланированное сканирование, поэтому ни одно не запускается, пока идёт другое, — сканирование с удалением или перемещением никогда не работает с папкой, которую читает догрузка. Письмо с ошибкой учитывается и пропускается.

Письма запрашиваются по 200 за раз. Вложения внутри пересланного письма (`message/rfc822`) тоже учитываются. Письма, уже помеченные `\Deleted`, игнорируются. Письмо, импорт которого продолжает завершаться ошибкой по причине, отличной от отклонения (ошибка хука, заполненный диск), повторяется при следующих двух сканированиях, а затем от него отказываются с ошибкой в логе, чтобы оно не задерживало почту после себя; позже его можно импортировать догрузкой. Отсечка по времени допускает отставание часов сервера от часов этого хоста на 10 минут.

Удаление и перемещение полагаются на UIDPLUS (или IMAP4rev2), чтобы окончательно удалять (expunge) только письма, принятые Lemmary. На сервере без этого расширения единственный способ окончательного удаления вычищает каждое письмо с флагом `\Deleted` в папке — включая те, которые пометил почтовый клиент и ещё не удалил окончательно, — поэтому Lemmary никогда его там не выполняет: удаление оставляет принятые письма помеченными `\Deleted`, а перемещение (при отсутствии и MOVE) копирует их в целевую папку и помечает оригинал до следующего окончательного удаления, которое выполнит собственный клиент пользователя.

- **Сервер IMAP** — `host` или `host:port`; порт по умолчанию — 993 для **TLS** и 143 для **STARTTLS**. Сертификат должен проходить проверку; IMAP открытым текстом не предлагается.
- **Имя пользователя**, **Пароль** — пароль доступен только для записи: API сообщает лишь, сохранён ли он, а сохранение с пустым полем оставляет его прежним.
- **Папка** — по умолчанию `INBOX`.
- **Импорт** — какие типы файлов становятся документами: **PDF**, **Office** (DOCX, XLSX), **Изображения** (JPG, PNG, WEBP) и **Текст** (TXT, CSV); по умолчанию все. Хранится как список пропускаемых типов (`imap_skip_types`); хотя бы один должен оставаться включённым. Письмо с вложением неотмеченного типа никогда не перемещается и не удаляется, как и письмо с отклонённым вложением, так что «Удалить» не может забрать файл, который так и не был импортирован; встроенные логотипы письмо не удерживают. Повторное включение типа не возвращается к уже просканированной почте; её подхватывает догрузка. Догрузка применяет тот же фильтр.
- **После импорта** — **Оставить** (по умолчанию) открывает папку только для чтения и запоминает наибольший принятый UID в журнале `ingest_files`, так что ни перезапуск, ни удаление документа не возвращают письмо; на сервере, сбрасывающем UIDVALIDITY, всё начинается заново, а проверка по контрольной сумме пропускает то, что уже есть в библиотеке. **Переместить** перемещает каждое принятое письмо в другую папку (создаётся, если её нет; она должна отличаться от исходной). **Удалить** помечает его `\Deleted` и окончательно удаляет. При шифровании хранимых данных перемещение или удаление ждёт, пока хранилище не запечатает документы.

Письмо, вложение которого отклонено (пустое, больше ограничения в 47 МБ, содержимое не соответствует расширению), никогда не перемещается и не удаляется; это записывается в лог, и письмо пропускается. Любая другая ошибка останавливает сканирование, и письмо повторяется в следующем интервале.

## Управление (интерфейс администратора) {#management-admin-ui}

**Управление** в навигации (только для администратора, под «Настройками») управляет учётными записями на экземпляре. Его вкладка **Пользователи** перечисляет все учётные записи `users`, добавляет новую (email, необязательное имя, пароль; создаётся подтверждённой, так что может сразу войти), изменяет email, имя или пароль обычной учётной записи и удаляет учётные записи. Удаление учётной записи удаляет также её документы, теги, общие доступы и ключи доступа. Учётные записи администраторов (`is_app_admin`) здесь перечислены, но доступны только для чтения; управляйте ими в панели PocketBase. Маршруты — `GET`/`POST /api/app/admin/users` и `PATCH`/`DELETE /api/app/admin/users/{id}`, только для администратора, с ответом `403` для учётной записи администратора. При включённом хранилище пароль новой учётной записи получает собственную обёртку ключа, как и у любой другой учётной записи.

## Обслуживание (интерфейс администратора) {#maintenance-admin-ui}

**Обслуживание** в навигации (только для администратора, рядом с «Настройками») содержит действия обслуживания, которые выполняются по всей библиотеке, а не для отдельного документа:

- **Искать дубликаты** — `POST /api/app/duplicates/scan`, см. [Поиск дубликатов](#duplicate-detection).
- **Сканировать почтовый ящик** (только при `INGEST_IMAP_ENABLED`) — `POST /api/app/ingest/imap/scan` с `{ "from": "YYYY-MM-DD", "to": "YYYY-MM-DD" }` запускает в фоне догрузку более старой почты, см. [Приём из IMAP](#ingest-from-imap), и отвечает `202` со статусом; `GET` по тому же пути возвращает `{ "running", "from", "to", "created", "skipped", "failed", "error" }` для последней догрузки, и страница опрашивает его каждые 3 с. `409`, пока идёт любое сканирование почтового ящика, `400` при неверных датах или отсутствии почтового ящика.
- **Очистить устаревшие данные** — `POST /api/app/taxonomy/prune` удаляет всех корреспондентов и все типы документов, на которые больше не ссылается ни один документ (оставшиеся после удалённых документов, переименований или прерванного импорта). Документы никогда не изменяются, как и теги: их создают вручную, поэтому тег без ссылок — это тег, который владелец ещё не применил, а не мусор. Ответ по-прежнему содержит счётчик `tags`, всегда `0`. Сбор ссылок и удаление выполняются в одной транзакции, поэтому документ, сохраняемый параллельно, либо учитывается как ссылка, либо не проходит собственную проверку связи; висячий идентификатор у него остаться не может.
  Кнопка неактивна, пока какое-либо задание обработки находится в состоянии `pending` или `running`, чтобы не смести сущность, которую задание вот-вот прикрепит. Число берётся из API коллекций PocketBase (`GET /api/collections/processing_jobs/records`), опрашивается каждые 5 с и перепроверяется при нажатии. Правило списка там — `document.user = @request.auth.id`, поэтому проверка видит только задания по собственным документам администратора — выполняющаяся загрузка другого пользователя кнопку не блокирует.
- **Перестроить поисковый индекс** — `POST /api/app/search/reindex`, см. [Полнотекстовый поиск](#full-text-search).
- **Построить эмбеддинги для N документов** — `POST /api/app/embeddings/backfill` обходит все документы, которым ещё нужны векторы фрагментов: архив, существовавший до привязки модели эмбеддингов, восстановленные резервные копии (их документы вообще не получают задания обработки), документы, изменённые после построения эмбеддингов, и всё, что сделала недействительным смена модели или разбиения на фрагменты. Он сразу отвечает `{ "started", "running", "stats" }` и обрабатывает накопившееся в фоне, пакетами, до 30 минут; `GET` по тому же пути возвращает `{ "running", "stats" }` — именно это строка прогресса опрашивает каждые 3 с. Раздел неактивен и указывает на «Настройки», если модель эмбеддингов не привязана (`409`), а кнопка неактивна, пока идёт обход. Обход и cron `EMBEDDING_BACKFILL_BATCH` используют одну блокировку, поэтому никогда не строят эмбеддинги для одного документа дважды, — а `EMBEDDING_BACKFILL_BATCH=0` отключает только cron, но никогда не эту кнопку.

Пункты меню навигации, доступные только администратору, отмечены значком щита (декоративным — эти пункты в любом случае отображаются только администраторам).

## Исходящая почта (SMTP / `outbound_emails`) {#outbound-mail-smtp-outbound-emails}

Настройте SMTP в PocketBase Admin → Settings → Mail. Когда SMTP **выключен** (по умолчанию), PocketBase обычно переходит на локальный `sendmail`. Это приложение заменяет такой запасной вариант: вместо этого сообщения записываются в коллекцию `outbound_emails` (сброс пароля, подтверждение, OTP, уведомления об аутентификации и т. д.).

Просматривайте их в PocketBase Admin под суперпользователем. Включите SMTP, когда нужна настоящая доставка; при включённом SMTP запись в базу данных не выполняется.

## Страница загрузки {#upload-page}

**Загрузка** (`/upload`) группирует способы попадания документов в библиотеку по подразделам, каждый на собственном маршруте, чтобы на раздел можно было дать ссылку, добавить его в закладки и вернуться к нему кнопкой «Назад» браузера:

| Раздел | Маршрут | Состояние |
| --- | --- | --- |
| Файлы | `/upload` (по умолчанию) | Реализовано — загрузка файлов или целых папок перетаскиванием или через выбор файлов, см. процесс обработки ниже |
| Сканирование | `/upload/scan` | Реализовано — сканирование со сканера eSCL (AirScan) в локальной сети, см. [Сетевое сканирование](/ru/scanning) |
| Заказы Amazon | `/upload/amazon` | Реализовано — импорт PDF-счетов из архива заказов, запрошенного у Amazon, см. [Импорт заказов Amazon](#amazon-order-import) |
| Zip-архив | `/upload/zip` | Реализовано — импорт документов из zip-архива, собранного пользователем, см. [Импорт zip-архива](#zip-archive-import) |
| Разделение документов | `/upload/split` | Реализовано — разделение PDF, содержащего несколько склеенных документов, на отдельный документ для каждой части, см. [Разделение документов](#document-splitting) |

Обычная загрузка файлов остаётся на самом `/upload` (индексный маршрут), поэтому существующие ссылки и пункт навигации **Загрузка** по-прежнему ведут на неё.

Папку можно перетащить на вкладку «Файлы» или выбрать через **Выбрать папку**, и браузер обходит её до самого дна: каждый файл внутри отправляется как отдельный документ, в точности как если бы он был выбран вручную. Файл, пришедший из папки, получает имя `<parent folder>-<file>` — то же правило, что и при импорте zip, потому что иначе сканер, записывающий `1.pdf` в отдельную папку для каждой партии, заполнил бы библиотеку документами с именем `1.pdf`. Остатки Finder и архиваторов молча отбрасываются, а не сообщаются как файлы неверного типа: `__MACOSX/`, теневые файлы AppleDouble `._` (у которых расширение файла, к которому они относятся) и любые другие файлы, начинающиеся с точки, — то же правило, что и при импорте zip. Брошенный сюда `.zip` не загружается; он указывает на вкладку «Zip-архив», которая может сначала показать, что содержит архив.

### Потолок страниц {#the-page-ceiling}

Одно ограничение не настраивается: **документ может
содержать не более 1000 страниц** на любой установке. Загрузка сверх этого
отклоняется с `limit_ocr_pages` до вызова какого-либо OCR-провайдера.

Оно существует из-за того, куда попадает текст. OCR-провайдеры возвращают весь текст
документа одной строкой, и эта строка должна поместиться в столбец `ocr_text`,
вмещающий 47 Mi символов — те же 47 МБ, которые принимает поле `documents.file`, но в
символах, а не в байтах. Больше ничто не ограничивает результат OCR: Mistral —
единственный провайдер, который документирует лимит страниц (1000 страниц, отсюда и
это число), а Google Vision читает столько страниц, сколько есть в файле, по пять за
раз. Число страниц, определённое до первого вызова провайдера, — единственное
измерение, которое говорит, можно ли будет сохранить ответ, а отказ на этом этапе
означает, что слишком длинный документ ничего не стоит, вместо того чтобы быть
оплаченным и затем отброшенным.

Следствия, которые стоит знать:

- У каждого загружаемого PDF страницы считаются с помощью `pdfinfo`; для других
  типов файлов это стоит чтения пятибайтового заголовка. PDF, число страниц
  которого не удаётся прочитать, считается одностраничным, поэтому на хосте без
  poppler этот потолок при загрузке не применяется — вместо этого слишком длинный
  результат отклоняет шаг OCR, и тогда ошибкой завершается документ, а не загрузка.
- Восстановление или импорт из Paperless-ngx, которые приносят текст документа с
  собой, пропускают потолок: OCR выполняться не будет, так что тратить нечего, а
  длинный документ, заархивированный до появления этого ограничения, остаётся
  восстановимым.
- DOCX и XLSX не ограничиваются числом страниц — у электронной таблицы их нет, —
  поэтому они измеряются по ходу разбора, и извлечение, выходящее за пределы
  столбца, прерывается с ошибкой, а не сохраняется урезанным. Это важно именно для
  XLSX: ячейки ссылаются на общую таблицу строк, поэтому текст, в который
  разворачивается файл, не ограничен числом байт, в котором он пришёл.

### Импорт заказов Amazon {#amazon-order-import}

Запросите архив у Amazon в разделе Account → Request your data → Your Orders; Amazon пришлёт письмо со ссылкой на скачивание, когда экспорт будет готов. Zip-архив содержит отчёты CSV, фотографии доставки и — в `Additional Data/Retail.TransactionalInvoicing.*` — PDF-счета. Импортируются только PDF; все остальные записи учитываются как проигнорированные и не затрагиваются.

Загрузка и импорт — это два шага, поэтому ничего не создаётся, пока пользователь не увидит, что содержит архив:

1. `POST /api/app/import/amazon/upload` (multipart, поле `file`) передаёт zip потоком в `<data dir>/temp/zip_import/` — он никогда не буферизуется в памяти, поскольку реальные экспорты достигают сотен МБ. Архив сканируется, для каждого PDF вычисляется хеш, и возвращается предпросмотр: общее число файлов, сколько из них можно импортировать, сколько дубликатов или слишком больших, число проигнорированных записей и список по файлам. Дубликаты — это PDF, контрольная сумма которых уже есть среди документов владельца (`duplicate_of` называет идентификатор существующего), или повторяющие файл, встретившийся раньше в том же архиве. Импортированные документы получают имена `<parent folder>-<file>`, потому что Amazon нумерует счета внутри каждой папки (`1.pdf`, `2.pdf`, …).
2. `POST /api/app/import/amazon` с `{ "upload_id": "..." }` запускает импорт и возвращает `202 Accepted` с `{ "job_id", "status": "running" }`. Опрашивайте `GET /api/app/import/amazon/status?job_id=...` для получения `progress` (`{ done, total }`), пока `status` не станет `completed` (с `result`) или `failed` (с `error`). `result` содержит счётчики `imported`, `skipped_duplicates`, `skipped_oversized` и `failed`, а также до 25 сообщений об ошибках по файлам. Каждый импортированный документ сохраняется как `pending`, поэтому проходит обычный [процесс обработки](#processing-flow) OCR + ИИ.

`DELETE /api/app/import/amazon/upload?upload_id=...` отбрасывает подготовленный архив, который пользователь решил не импортировать. Подготовленные архивы истекают через 30 минут и удаляются при следующей загрузке, включая файлы, оставшиеся от предыдущего процесса, — реестр подготовленных загрузок и состояние заданий хранятся в памяти, поэтому и то и другое теряется при перезапуске. Загрузка второго архива также отбрасывает предыдущий архив учётной записи, так что у учётной записи одновременно есть не более одного. Подтверждение расходует идентификатор загрузки: один и тот же архив нельзя импортировать дважды, и для одного пользователя одновременно может выполняться только один импорт (повторный запуск возвращает `409`).

Отклонения возвращаются как `400` на этапе предпросмотра, а не посреди импорта: нечитаемый zip, отсутствие PDF, больше 5000 PDF, загрузка больше `IMPORT_STAGING_MAX_BYTES` (по умолчанию 1 ГиБ) или архив, распаковывающийся больше чем в 8 ГиБ (zip-бомба). Отдельный PDF больше лимита `documents.file` в 47 МБ не фатален — он помечается как `oversized` в предпросмотре и пропускается при импорте. PDF сверх [потолка страниц](#the-page-ceiling) отклоняется для каждой записи по ходу прогона, а не на этапе предпросмотра, поскольку реальное число страниц в архиве можно узнать, только открыв каждый PDF в нём.

### Импорт zip-архива {#zip-archive-import}

Те же два шага, что и при импорте Amazon выше, через `/api/app/import/zip/upload`, `/api/app/import/zip` и `/api/app/import/zip/status`, с идентичными телами запросов, лимитами и отклонениями. Это одна и та же реализация: единственное различие между двумя сценариями — какие записи в архиве считаются документами; это указывает маршрут загрузки, а затем запоминает подготовленная загрузка.

Здесь это означает любой тип, который может хранить `documents.file`, — PDF, JPEG, PNG, WebP, простой текст, CSV, `.docx` и `.xlsx`, — а не только PDF. Всё остальное в архиве учитывается как проигнорированное и не затрагивается, как и записи каталогов, пустые записи и служебные файлы архиваторов (`__MACOSX/`, файлы AppleDouble `._`). Импортированные документы получают имена `<parent folder>-<file>`, так что zip с результатами работы сканера остаётся понятным.

Список расширений — это предварительный фильтр, а не последнее слово: PocketBase решает, что принимает поле `file`, анализируя содержимое при сохранении, поэтому запись, расширение которой не соответствует содержимому, отклоняется там и отображается среди ошибок прогона по файлам, а не на этапе предпросмотра.

Подготовленный архив и выполняющийся импорт — по одному на учётную запись для обоих zip-сценариев, поэтому загрузка экспорта Amazon отбрасывает zip, подготовленный мгновением раньше, а второй импорт во время выполнения первого возвращает `409`. Восстановление резервной копии Lemmary — совсем другое дело, оно находится на [`/import/archive`](#restoring); у него собственная подготовка, и оно может выполняться параллельно.

### Сетевое сканирование {#network-scanning}

**Сканирование** (`/upload/scan`) сканирует с устройства eSCL («AirScan») в локальной сети и добавляет страницы как один документ. Настройка, два способа обнаружения сканеров и то, почему mDNS требует `network_mode: host` в Docker, описаны в разделе [Сетевое сканирование](/ru/scanning); API такой:

1. `GET /api/app/scan/discover?cidr=...` возвращает `{ scanners, cidr }`. Обнаружение — это просмотр mDNS для `_uscan._tcp`/`_uscans._tcp` и обход `cidr` с запросами `GET http://<ip>/eSCL/ScannerCapabilities`, выполняемые параллельно и объединяемые по адресу; оба укладываются в общий бюджет в 5 секунд. Если `cidr` не указан, он выводится как /24 от клиентского адреса запроса — это единственная подсказка о локальной сети, которая есть у приложения в контейнере, — и возвращается в ответе, чтобы интерфейс мог сказать, где шёл поиск. Диапазон, который не является частным или больше /22, отклоняется с `400`.
2. `POST /api/app/scan` с `{ "scanner", "source", "upload_id" }` возвращает `202 Accepted` и `{ "job_id" }`. `source` — это `platen` (одна страница) или `feeder` (все листы за одно задание). Пустой `upload_id` начинает новый документ; иначе страницы добавляются к указанному. Опрашивайте `GET /api/app/scan/status?job_id=...` до `completed`, где `result` — подготовленный документ: `upload_id`, `page_count`, `size_bytes`, `expires_at`. Для одного пользователя одновременно выполняется одно сканирование (повторный запуск возвращает `409`), и это же не даёт двум прогонам слиться в один файл.
3. `GET /api/app/scan/pdf?upload_id=...` передаёт потоком документ в текущем состоянии для предпросмотра. `DELETE /api/app/scan?upload_id=...` отбрасывает его.
4. `POST /api/app/scan/document` с `{ "upload_id" }` сохраняет его как документ `pending` и возвращает `{ "document_id" }`, так что он проходит обычный [процесс обработки](#processing-flow) OCR + ИИ. Повторное сканирование того, что уже есть в библиотеке, возвращается как `400` с `duplicate_of`.

Само сканирование — это три запроса к устройству: `POST {base}/ScanJobs` с документом PWG ScanSettings (A4, 300 dpi, RGB24, `application/pdf`), затем `GET {job}/NextDocument`, пока он не ответит `404`, затем `DELETE {job}` — удаление выполняется всегда, в том числе после сбоя, потому что устройство с незакрытым заданием отклоняет следующее. Страницы объединяются с помощью `pdfunite` в `<data dir>/temp/scan/<upload id>.pdf`, срок действия которого, как и у любой другой подготовленной загрузки, истекает через 30 минут.

Поскольку адрес приходит от того, кто вошёл в систему, каждый запрос проходит через защиту на этапе установки соединения, которая разрешает только адреса RFC1918 и IPv6 ULA: публичные адреса, `localhost` и link-local `169.254.x` (сервис облачных метаданных) отклоняются, перенаправления не выполняются, а заголовок `Location`, указывающий на другой хост, отвергается. Размер подготовленного документа ограничен собственными 47 МБ поля `documents.file`; это проверяется перед каждым сканированием, чтобы о заполненном документе сообщалось, пока с этим ещё можно что-то сделать.

### Разделение документов {#document-splitting}

**Разделение документов** (`/upload/split`) принимает PDF, содержащий несколько отдельных документов, отсканированных в один файл, и создаёт по документу на каждую часть. Подготовленный оригинал отбрасывается — документами становятся только части.

Загрузка и разделение — это два шага, поэтому ничего не создаётся, пока пользователь не решит, где проходят разрезы:

1. `POST /api/app/split/upload` (multipart, поле `file`) передаёт PDF потоком в `<data dir>/temp/split_upload/<upload id>/source.pdf` и рендерит рядом по миниатюре на страницу размером 900 px по длинной стороне — больше, чем 400 px превью на карточке документа, потому что чтобы решить, где заканчивается документ, нужно прочитать бланк на странице (один запуск `pdftoppm`; `pdftoppm` дополняет номера в своих выходных файлах нулями, поэтому файлы переименовываются в `page-<n>.png`). Ответ содержит `upload_id`, `file_name`, `page_count`, `size_bytes` и `expires_at`.
2. `GET /api/app/split/page?upload_id=...&page=n` отдаёт одну закешированную миниатюру как `image/png`. Эндпоинту нужен токен сеанса, который `<img src>` передать не может, поэтому SPA запрашивает каждую страницу и оборачивает её в blob URL.
3. `POST /api/app/split` с `{ "upload_id": "...", "parts": [{ "from": 1, "to": 2 }, …] }` запускает разделение и возвращает `202 Accepted` с `{ "job_id", "status": "running" }`. Опрашивайте `GET /api/app/split/status?job_id=...` для получения `progress` (`{ done, total }`), пока `status` не станет `completed` (с `result`) или `failed` (с `error`). `result` содержит счётчики `created`, `skipped_duplicates`, `skipped_oversized` и `failed`, а также до 25 сообщений об ошибках по частям и созданные `document_ids`. Каждая часть сохраняется как `pending`, поэтому проходит обычный [процесс обработки](#processing-flow) OCR + ИИ.

`parts` должны покрывать каждую страницу ровно один раз и по порядку — только это и может выразить интерфейс разметки разрезов, поэтому пропуск, перекрытие, неотсортированный список или диапазон за пределами файла возвращаются как `400` с сообщением, называющим страницу, на которой возникла проблема. Отклонённый запрос оставляет загрузку подготовленной, так что за ним может последовать исправленный.

Части получают имена по содержащимся в них страницам (`scan-page-1.pdf`, `scan-pages-2-5.pdf`) на основе очищенного имени загруженного файла. `pdfseparate` и `pdfunite` копируют исходные объекты страниц, а не растеризуют их заново, поэтому текстовый слой и качество изображений сохраняются; обе утилиты вписывают в результат случайный `/ID` в трейлере, который переписывается на фиксированное значение, чтобы извлечение одних и тех же страниц дважды давало одинаковые байты. Без этого проверка точных дубликатов никогда не распознала бы повторно разделённую часть, и двойное разделение одного и того же скана молча создало бы вторую копию всего. Перезапись выполняется только тогда, когда `/ID` находится за смещением, указанным в `startxref` (чтобы ни одно смещение в таблице перекрёстных ссылок не сдвинулось), и откатывается, если результат не открывается.

`DELETE /api/app/split/upload?upload_id=...` отбрасывает подготовленный PDF, который пользователь решил не разделять. Подготовленные загрузки истекают через 30 минут и удаляются при следующей загрузке, включая каталоги, оставшиеся от предыдущего процесса, — реестр подготовленных загрузок и состояние заданий хранятся в памяти, поэтому и то и другое теряется при перезапуске. Подтверждение расходует идентификатор загрузки: один и тот же PDF нельзя разделить дважды, и для одного пользователя одновременно может выполняться только одно разделение (повторный запуск возвращает `409`).

Отклонения возвращаются как `400` на этапе загрузки: нечитаемый PDF (решают заголовок `%PDF-` и `pdfinfo`, а не заявленный тип содержимого), одностраничный PDF (нечего разделять), больше 100 страниц или загрузка больше 100 МиБ. Часть больше лимита `documents.file` в 47 МБ не фатальна — она учитывается как `skipped_oversized`.

#### Автоматическое определение {#automatic-detection}

`POST /api/app/split/detect` с `{ "upload_id": "..." }` предлагает разрезы и возвращает `202 Accepted` с `job_id`; опрашивайте `GET /api/app/split/detect/status?job_id=...` тем же способом. `result` — это `{ "parts": [{ "from", "to", "title" }], "text_source" }`. Определение не расходует загрузку: его можно повторять, а разделение пользователь всё равно подтверждает сам.

Текст страниц сначала берётся из `pdftotext` постранично (`text_source: "pdf"`). Считается, что у страницы есть текстовый слой, если на ней 16 символов или больше; когда этот порог проходят меньше половины страниц, файл считается сканом и каждая страница вместо этого читается настроенным OCR-провайдером (`text_source: "ocr"`) — подсчёт ведётся постранично, а не по среднему, поскольку одна изначально цифровая титульная страница перед тридцатью отсканированными иначе подняла бы среднее выше любого порога. Запасной вариант с OCR извлекает каждую страницу в отдельный PDF и ограничен 40 страницами; сверх этого задание завершается ошибкой с сообщением, предлагающим пользователю разметить разрезы вручную. Для определения нужна модель извлечения (иначе `400`), а для скана — ещё и OCR-провайдер.

Тексты страниц отправляются провайдеру и модели извлечения одним запросом с просьбой вернуть `{"parts":[{"from","to","title"}]}`, с бюджетом символов на страницу `max(200, 30000 / pages)`, так что даже 100-страничный файл приходит целиком, а не усечённым до первых страниц. Затем ответ нормализуется на сервере в непрерывное покрытие всех страниц: сохраняются только подразумеваемые им позиции разрезов, и части строятся заново по ним, так что неотсортированное предложение, с пропусками, перекрытиями или выходом за диапазон, всё равно даёт то, что принимает `POST /api/app/split`, а непригодное деградирует до одной части на весь файл.

## Резервное копирование и восстановление {#backup-and-restore}

Любой вошедший пользователь может скачать всю свою библиотеку одним zip-архивом и восстановить её — в этот экземпляр или в другой. Полная резервная копия создаётся для каждого пользователя отдельно: она содержит документы и таксономию вызывающего пользователя, никогда — чьи-либо ещё и никогда — настройки экземпляра или API-ключи. Сохранённые чаты с ИИ не включаются: экспорт переносит архив, а не разговоры о нём.

### Экспорт {#exporting}

**Ещё → Экспорт → Скачать резервную копию** или `POST /api/app/documents/export` без тела. Ответ передаёт потоком zip с именем `lemmary-export.zip`.

Чтобы экспортировать только часть библиотеки, отфильтруйте список «Документы» и воспользуйтесь значком скачивания рядом с **Поиском с ИИ**. Тогда отправляется `{"ids": [...]}`, и архив содержит только те из этих документов, которые вызывающий пользователь может читать, включая общие, а также только теги, корреспондентов и типы документов, которые у них есть.

Все записи лежат плоско в `lemmary-export/`, так что архив остаётся удобным для просмотра вручную:

```text
lemmary-export/manifest.json
lemmary-export/<date> [<id>] <title><ext>              the original upload
lemmary-export/<date> [<id>] <title>.ocr.txt           extracted text (omitted when empty)
lemmary-export/<date> [<id>] <title>.metadata.json     titles, tags, dates, checksum, timestamps
lemmary-export/<date> [<id>] <title>.preview.png       generated thumbnail (omitted when there is none)
```

`<date>` — собственная дата документа в формате `YYYY-MM-DD`, поэтому сортировка файлов по имени сортирует их по дате. Для документа без даты она опускается, и его записи сортируются после датированных. Архивы, созданные до появления префикса с датой, восстанавливаются так же. `<title>` очищается и усекается так, чтобы самое длинное имя укладывалось в ограничение в 255 байт, которое файловые системы накладывают на один элемент пути. Связи записываются **именами**, а не идентификаторами, потому что идентификаторы ничего не значат в экземпляре, куда восстанавливается архив.

`manifest.json` — это оглавление: `format`, `version`, `exported_at`, `document_count`, полная `taxonomy` и точные пути записей каждого документа. От него зависят две вещи:

- **Теги, корреспонденты и типы документов, на которые не ссылается ни один документ.** Больше нигде в архиве их нет, поэтому без манифеста восстановление их потеряло бы.
- **Различение сопутствующих файлов.** Документ, собственный файл которого — `.txt` с именем, как у сопутствующего OCR-файла, невозможно отличить от такого файла только по имени.

Документ, сохранённый файл которого отсутствует в хранилище, пропускается и не попадает в манифест, так что манифест никогда не заявляет того, чего в архиве нет.

### Восстановление {#restoring}

**Ещё → Импорт** (`/import`) или API ниже. Архив передаётся потоком в `<data dir>/temp/archive_import/` — никогда не буферизуясь в памяти, — затем сканируется, и показывается предпросмотр: сколько в нём документов, сколько из них новых, сколько дубликатов, слишком больших или отсутствующих, сколько таксономии приходит вместе с ними. Ничего не создаётся, пока вы не подтвердите.

Два режима:

- **Восстановить архив как был** (`restore`, по умолчанию): воссоздаёт заголовки, теги, корреспондентов, типы документов, даты, OCR-текст и миниатюры, причём таксономия восстанавливается первой, чтобы записи, на которые ничто не ссылается, тоже попали на место. Восстановленные документы **вообще не получают задания обработки** — всё, что вывел бы конвейер, уже есть в архиве, — поэтому восстановление **не делает ни одного вызова OCR или LLM** и не может перезаписать только что восстановленное. Для документа, у которого в архиве нет `.metadata.json`, восстанавливать нечего, поэтому он идёт обычным путём загрузки; такие документы есть только в архивах `originals`, созданных до появления манифеста.
- **Импортировать только файлы и обработать заново** (`reprocess`): игнорирует все сопутствующие файлы и ставит в очередь полный конвейер OCR + ИИ, как для новой загрузки.

Поскольку восстановление не запускает конвейер, поиск почти-дубликатов по восстановленным документам заново не выполняется. Точные дубликаты по-прежнему отклоняются при создании по контрольной сумме, а `duplicate_of` / `text_fingerprint` возвращаются из архива; **Обслуживание → Искать дубликаты** заново выводит связи почти-дубликатов по всей библиотеке, когда вы хотите их пересчитать. Восстановленный документ также сохраняет ту миниатюру, которая была в архиве, — старый архив без сопутствующих файлов `.preview.png` оставляет эти документы без миниатюры, пока их не обработают заново.

Чего восстановление *не* сохраняет: **идентификаторов документов**. Восстановленные документы получают новые идентификаторы, а `duplicate_of` переназначается на восстановленную копию, если оригинал находится в том же архиве (и отбрасывается, если нет). `created` и `updated` записываются обратно после сохранения, так что библиотека возвращается в исходном порядке. Документы, контрольная сумма файла которых уже есть в вашей библиотеке, пропускаются, поэтому повторное восстановление того же архива безопасно.

Архивы, экспортированные до появления манифестов, по-прежнему восстанавливаются: их документы воссоздаются только по именам записей. Из них нельзя восстановить лишь осиротевшую таксономию — и тот единственный случай с файлом, похожим на сопутствующий.

### API {#api}

1. `POST /api/app/import/archive/upload` (multipart, поле `file`) подготавливает zip и возвращает предпросмотр, включая `upload_id` и `has_manifest`.
2. `DELETE /api/app/import/archive/upload?upload_id=...` отбрасывает подготовленный архив. Подготовленные архивы также сами истекают через 30 минут.
3. `POST /api/app/import/archive` с `{ "upload_id": "...", "mode": "restore" | "reprocess" }` возвращает `202 Accepted` с `{ "job_id", "status": "running" }`.
4. `GET /api/app/import/archive/status?job_id=...` — пока `status` не станет `completed` (с `result`) или `failed` (с `error`).

Состояние задания хранится в памяти только для работающего процесса, и для одного пользователя одновременно может выполняться один импорт. Подготовка нового архива отбрасывает предыдущий архив учётной записи, так что у учётной записи одновременно есть не более одного. Загрузки ограничены `IMPORT_STAGING_MAX_BYTES` (по умолчанию 1 ГиБ) и 5000 документами, каждая запись — лимитом документа в 47 МБ; один общий бюджет охватывает всё, что распаковывают проверка и восстановление, так что архив, который разворачивается далеко за пределы своего размера, отклоняется как zip-бомба. Восстановленный документ, у которого есть собственный сопутствующий OCR-файл, освобождается от [потолка страниц](#the-page-ceiling) — ему не нужен OCR, поэтому длинный документ, заархивированный до появления этого потолка, по-прежнему восстанавливается; запись без сопутствующего файла идёт обычным путём загрузки, и на неё потолок распространяется.

Архив без документов, но с непустой таксономией корректен и восстанавливается — так выглядит резервная копия библиотеки с тегами, но без документов.

## Процесс обработки {#processing-flow}

1. Пользователь загружает документ на `/upload`
2. PocketBase сохраняет файл и создаёт запись `processing_jobs` через хук Go
3. Хук `OnRecordAfterCreateSuccess` сразу запускает задание; cron-задание (`process_pending_jobs`) подбирает зависшие ожидающие задания
4. Воркер генерирует PNG-превью первой страницы PDF (через `pdftoppm`), затем извлекает текст, при необходимости проверяет почти-дубликаты и запускает извлечение метаданных ИИ
5. Извлечённые метаданные сохраняются в документе
6. Интерфейс показывает статус в списке и на странице документа, а всё, что ждёт человека, появляется во [Входящих для проверки](#review-inbox)

Извлечение метаданных отправляет настроенному провайдеру LLM OCR-текст текущего документа **и** до 500 имён существующих корреспондентов и типов документов этого владельца, чтобы модель могла повторно использовать существующие метки, а не создавать почти-дубликаты. Имена отправляются как массив JSON, помеченный как недоверенные данные. Шаг применения по-прежнему сопоставляет точные имена, а затем форму без учёта пунктуации и диакритики (`Amazon EU S.à r.l.` и `Amazon EU S.a.r.l.`). Существующее имя при повторном использовании не перезаписывается.

### Пользовательские поля {#custom-fields}

Администратор задаёт дополнительные поля документов в Настройки → Обработка → **Пользовательские поля документов**: название, тип (текст, число или дата) и необязательную подсказку для извлечения, например *рядом с «Счёт №»*. Название и подсказка попадают в промпт, с которым модель извлечения читает каждый документ, поэтому в подсказке стоит объяснить, что означает поле и где его найти. Поля действуют для всего экземпляра, и каждая страница документа их показывает; читатели общего документа видят значения только для чтения. Это записи коллекции `custom_fields`: читать её может любой вошедший пользователь, а менять — только администратор.

Извлечение запрашивает у модели каждое поле по названию и **заполняет только пустые**: введённое вручную значение переживает любую повторную обработку. Чтобы заменить значения, при повторной обработке документа отметьте **Перезаписать пользовательские поля** под шагом *Применение метаданных*: каждое поле, для которого извлечение нашло значение, перезаписывается, остальные сохраняют свои. Число возвращается обычным числом, дата — в виде `YYYY-MM-DD`, а ответ, не подходящий к типу поля, отбрасывается. Если поля не заданы, промпт извлечения остаётся точно таким же, как прежде.

Каждое значение — строка `custom_field_values` (документ, поле и столбец `text`, `number`, `date` или `option`), поэтому при переименовании поля значения сохраняются, а тип поля после сохранения не меняется. Удаление поля удаляет его значения. Корреспондент и тип документа — два предопределённых поля того же рода: их значения ссылаются на собственный список названий владельца в `custom_field_options`, который извлечение и страница документа пополняют и переиспользуют и который API paperless-ngx отдаёт как свои корреспонденты и типы документов. Значения входят в [полнотекстовый поиск](#full-text-search). [Экспорт](#exporting) записывает их по названиям полей, а импорт восстанавливает значение только в поле, которое на этом экземпляре задано под тем же названием, поэтому создайте поля до импорта.

### Входящие для проверки {#review-inbox}

**Входящие** в шапке — это список документов со статусом `needs_review`: всё, что ждёт вас, а не воркер. Там показывается счётчик, так что достаточно взглянуть на шапку, чтобы понять, есть ли что делать.

Документ попадает туда по одной из трёх причин:

- **Низкая уверенность извлечения** — модель оценила собственный ответ ниже 0,5.
- **Возможный дубликат** — см. [поиск дубликатов](#duplicate-detection) ниже; карточка и страница документа ссылаются на документ, дубликатом которого он может быть.
- **Потому что вы попросили все** — Настройки → **Всегда требовать проверку новых документов** (включено для нового экземпляра; обновлённый сохраняет свою настройку). Когда это включено, каждый документ, для которого ИИ извлёк метаданные, ждёт во Входящих, каким бы уверенным ни было извлечение, включая документы, обработанные заново: ничто не доходит до `completed`, пока вы этого не скажете. Эта настройка — для рабочего процесса, когда документы загружаются по мере поступления, а исправляется накопившееся за месяц за один присест.

  Она не применяется к импорту из paperless-ngx в режиме сохранения. Там извлечение ИИ не выполняется — метаданные те, что были выверены в paperless, — так что проверять нечего, и перенесённый архив не вываливается во Входящие.

  Включение также перестраивает два списка вокруг неё, потому что иначе **Документы** были бы в основном второй копией Входящих:

  - **Документы** по умолчанию показывают **Завершённые** — архив, который вы действительно прочитали. Выпадающий список статусов по-прежнему предлагает *Все статусы*, и выбор этого пункта добавляет в URL `?status=all`.
  - Загрузка нескольких файлов, импорт Amazon и разделение завершаются во **Входящих**, а не в **Документах**, которые отфильтровали бы как раз то, что только что добавлено. Загрузка одного файла по-прежнему открывает этот документ.

  Экземпляр сообщает об этой настройке в `GET /api/app/meta`, чтобы SPA могло делать и то и другое для каждого пользователя, а не только для администраторов; изменить её может только администратор.

Два способа выйти оттуда, и оба ставят статус `completed`:

- **Сохранить исправления** на странице документа — исправление неверно прочитанной `document_date` и сохранение считается проверкой.
- **Отметить как проверенный**, когда метаданные уже верны, — на странице документа, на карточке в списке или сразу для выбора карточек во Входящих. Записывается только статус, поэтому `metadata_source` по-прежнему фиксирует, что метаданные написала модель.

При включённой настройке **Всегда требовать проверку** извлечение также просит модель предложить до трёх **предлагаемых тегов**: новых имён, которых ещё нет в вашем словаре. Пока документ ждёт, они показываются на карточке и на странице документа как чипы `+ name` с пунктирной рамкой, и принятие такого чипа создаёт тег и добавляет его к документу. Предложения хранятся в задании обработки, никогда в документе, и исчезают после проверки. В остальных случаях ИИ никогда не создаёт теги.

Документ, отмеченный как проверенный при заданном `duplicate_of`, сохраняет эту связь: отношение по-прежнему верно, а отметка о проверке говорит, что вы посмотрели и оставили оба.

### Поиск дубликатов {#duplicate-detection}

- **Точные дубликаты** — при создании для загруженного файла вычисляется хеш (SHA-256) в `documents.checksum`. Вторая загрузка с той же контрольной суммой для того же пользователя **отклоняется** с ошибкой, указывающей на идентификатор существующего документа. Уникальность обеспечивается уникальным индексом по непустым контрольным суммам для каждого пользователя, поэтому параллельные загрузки не могут обе завершиться успехом.
- **Почти-дубликаты (необязательно)** — после OCR шаг `detect_duplicates` может сравнивать нормализованный OCR-текст (SimHash + Jaccard). Это управляется настройкой Настройки → **Включить поиск почти-дубликатов после OCR** (по умолчанию выключено). Совпадения помечаются `needs_review`, а `duplicate_of` указывает на более ранний документ (никогда на более новый), поэтому они появляются во [Входящих](#review-inbox); шаги извлечения и применения ИИ пропускаются.
- **Массовое сканирование** — Обслуживание → **Искать дубликаты** (администратор) заполняет отсутствующие контрольные суммы и отпечатки и помечает точные (и, если включено, почти) дубликаты среди существующих документов.

Извлечение текста:

- **PDF и изображения** — настроенный OCR-провайдер (Google Vision, Mistral Document OCR, модель OpenAI/OpenRouter, принимающая файлы и изображения, или [локальный сайдкар Docling](/ru/local_ocr))
- **TXT, CSV, DOCX, XLSX** — встроенные парсеры (без вызова OCR API); для этих форматов превью не создаётся. DOCX или XLSX, текст которого не помещается в `ocr_text`, приводит к ошибке документа, а не сохраняется урезанным; см. [потолок страниц](#the-page-ceiling)

Cron-задания видны и запускаются вручную в PocketBase Admin → Settings → Crons.

## Полнотекстовый поиск {#full-text-search}

Поиск по архиву использует инвертированный индекс [Bleve](https://github.com/blevesearch/bleve) (а не SQLite `LIKE`). Индекс находится в `{dataDir}/bleve/documents` (Docker: `/app/pb_data/bleve/documents` на существующем томе `app_data`). Это производные данные: очистка `pb_data` очищает и индекс, а следующая загрузка перестраивает его по документам.

Поведение запросов:

- Термины объединяются через **AND** (должны совпасть все) и ранжируются по **BM25**. Фразы в кавычках `"phrases"` должны встречаться по порядку, а запрос в поле поиска с такой фразой ничего не добавляет по смыслу: кавычки требуют именно эти слова. **Найти документы** на странице «Теги» ищет имя тега именно так.
- **Когда точных совпадений нет, термины из трёх букв и длиннее повторно ищутся как префиксы** — `amaz` находит *Amazon*, пока вы ещё печатаете, `Rechnung` находит *Rechnungsnummer*. Точные и префиксные совпадения никогда не смешиваются: повторный поиск выполняется только тогда, когда поиск по целым словам ничего не вернул, поэтому документ, действительно содержащий слово, никогда не оттесняется документом, в котором лишь есть слово, начинающееся с него. Термины, содержащие цифру, исключаются (`202` был бы префиксом каждого года в архиве), и это префикс, а не подстрока — `mazon` по-прежнему ничего не находит.
- Поиск охватывает заголовок, сводку, OCR-текст, имена тегов, типов и корреспондентов, `people_or_organizations`, а также значения [пользовательских полей](#custom-fields).
- Поле поиска на главной странице вызывает `GET /api/app/documents/search`, как только введены три символа, — до этого оно сообщает об этом и оставляет список без фильтра, поскольку одно- или двухбуквенный префикс совпал бы с большей частью архива. Пустое поле поиска по-прежнему выводит список через PocketBase (сортировка по дате создания).
- Инструмент `search_documents`, стоящий за обеими [страницами поиска](/ru/deep_research), и `GET /api/documents/?query=` в paperless-ngx используют тот же индекс. `read_documents` в Deep Research читает `ocr_text` прямо из базы данных, а не из индекса.
- **Поиски агента ослабляют это AND, а поле поиска — нет** (при наличии модели эмбеддингов оно добавляет документы, близкие по смыслу, см. ниже). Промпты просят модель развернуть вопрос в ключевые слова, и требование совпадения всех из них ничего не находило в архивах, где на каждое ключевое слово приходилось по документу. Поэтому `search_documents` требует большинства терминов (все из 2, n−1 до 5, затем 70%), а если и *это* ничего не находит, повторяет поиск по любому из них — с допуском в одну правку для слов из пяти букв и длиннее, не содержащих цифр, — ограничивая повторный поиск 10 совпадениями. Фраза в кавычках остаётся обязательной в обеих попытках. Поле поиска намеренно сохраняет строгое AND: там запрос — это фильтр по документам, которые пользователь знает, и совпадение, в котором пропало слово, выглядит как ошибка.
- Фильтры коллекций PocketBase (`field ~ "..."`) остаются доступными для клиентов API; интерфейс больше не использует их для поля поиска.

Когда привязана модель эмбеддингов, рядом появляется второй индекс в
`{dataDir}/bleve/chunks`: по одной записи на каждый фрагмент с эмбеддингом, с текстом
фрагмента и его вектором. К нему обращается поисковый агент, а также поле поиска:
там каждое строгое совпадение по ключевым словам ранжируется вместе с не более чем 20
документами, фрагменты которых выделяются среди остальных по смыслу (reciprocal rank
fusion, фильтры списка применяются к обоим), так что перефразировка или слово на
другом языке всё равно находят свой документ. Смысл переупорядочивает совпадения по
ключевым словам, но никогда не ставит результаты выше них: документы, найденные только
по смыслу, идут после последнего документа, содержащего слова. Ближайшего соседа
недостаточно: документ учитывается, когда его сходство превышает медианный документ
запроса на 15% запаса над этой медианой или, для `bge-m3`, когда оно достигает 0,48 —
это единственная модель с измеренным порогом и единственный способ, которым «invoice»
находит архив немецких счетов, получающих одинаковые оценки. По не относящемуся к
архиву запросу ничего не выводится. Каждый запрос в поле поиска стоит одного запроса
эмбеддинга. Это производные данные, как и первый индекс, — они перестраиваются из
`data.db` без вызовов провайдера эмбеддингов, — и индекс версионируется по модели *и*
числу измерений, так что смена любого из них очищает и заново заполняет только этот
индекс, пока поиск по ключевым словам продолжает работать. Снятие привязки
эмбеддингов удаляет каталог.

Администраторы могут принудительно перестроить индекс через **Обслуживание → Перестроить поисковый индекс** (`POST /api/app/search/reindex`). Перестраиваются оба индекса.

## Сеансы чата {#chat-sessions}

Обе страницы поиска (`/rag/search`, `/rag/research`) и страница **Спросить ИИ** документа (`/document/<id>/ask`) сохраняют свои разговоры. Каждая страница перечисляет прошлые чаты на боковой панели, даёт открытому чату собственный URL (`/rag/search/<chatId>`, `/rag/research/<chatId>`, `/document/<id>/ask/<chatId>`) и позволяет переименовать или удалить чат. Одна боковая панель обслуживает обе страницы поиска: чат виден на любой из них и открывается по тому пути, на котором выполнялся.

Переписка принадлежит серверу. Запрос содержит идентификатор сеанса и одно новое сообщение — `POST /api/app/search` с `{"session_id": "...", "content": "...", "mode": "search|research"}`, `POST /api/app/documents/<id>/chat` с `{"session_id": "...", "content": "..."}`, — а история читается из базы данных, а не воспроизводится браузером. Если `session_id` не указан, начинается новый чат, названный по первому сообщению.

`POST /api/app/search/stream` принимает то же тело и сохраняет так же; поскольку его строка статуса уходит вместе с первым событием шага, сохранённая реплика приходит как событие `saved`, закрывающее поток, а не как тело ответа. Через него идут обе страницы — Deep Research ради событий шагов, Поиск с ИИ ради heartbeat-сообщений под ответом, поскольку для прокси с таймаутом чтения ответ, который ничего не пишет, пока не будет готов результат, неотличим от зависшего бэкенда. При повторном открытии чата поиска восстанавливается страница, на которой выполнялась его последняя реплика.

Прогон не заканчивается вместе с соединением. Потеря потока стоит отображения прогона в реальном времени, но не самого прогона: он завершается, и реплика сохраняется, так что обрыв сети посреди ответа оставляет чат ждать на боковой панели, а не теряет ответ, за который провайдеру уже заплачено. Поэтому отмена выражается явно — отправьте `run_id` вместе с запросом и `POST /api/app/search/cancel` с `{"run_id": "..."}`, чтобы остановить прогон. Неотменённый прогон завершается по собственному бюджету — 20 минут.

Чат создаётся сразу после отправки первого сообщения, до вызова модели, поэтому весь прогон происходит внутри разговора, в котором он будет сохранён, — этот идентификатор также является `x-opencode-session`, который передаёт запрос OpenCode, так что все реплики одного чата используют общий кеш промпта. Первая реплика, так и не давшая ответа, забирает свой чат с собой, так что неправильно настроенный провайдер или провайдер с таймаутом не оставляет пустых чатов. Превышение лимита в 500 чатов отклоняется заранее с `409`, а не после того, как за ответ уже заплачено. Если ответ получен, но сохранить его не удаётся, ответ содержит `"saved": false`, и ответ показывается без добавления в историю.

Управление сохранёнными чатами:

| Маршрут | Назначение |
| --- | --- |
| `GET /api/app/chats` | Список чатов. Фильтры: `kind=search\|document`, `document=<id>`; постранично с `page` / `perPage` |
| `GET /api/app/chats/{id}` | Один чат с его сообщениями |
| `PATCH /api/app/chats/{id}` | Переименование (`{"title": "..."}`) |
| `DELETE /api/app/chats/{id}` | Удаление чата и его сообщений |

Список чатов не разбивается на страницы: один запрос возвращает все чаты, которые может хранить учётная запись, а боковая панель прокручивается. Чтение переписки ограничено, и ограничение отбрасывает самые старые реплики — `truncated` сообщает, что потеряно начало, но никогда не актуальный конец.

Ограничения:

- У сообщения нет собственного ограничения длины; тело запроса ограничено 2 МБ. Длинный вопрос стоит контекстного окна модели, и поле ввода исследования сообщает об этом до отправки, когда размер окна известен.
- Модель видит переписку целиком, до 500 последних строк за одно чтение. Больше ничто её не урезает: единственное ограничение — контекстное окно провайдера, и разговор, переросший его, завершается собственной ошибкой провайдера, а не тихо теряет самые старые реплики. Реплики исследования сообщают, что они использовали, — см. [AI-провайдеры → Каталог моделей](/ru/ai_providers#the-model-catalogue).
- Чат **исследования** хранит больше, чем разговор. Вызовы инструментов каждой реплики и всё, что вернули инструменты, сохраняются по мере выполнения и воспроизводятся со следующим вопросом, так что уточняющий вопрос опирается на найденное в предыдущих репликах, а не читает те же документы заново, — и прогон, который был отменён, отклонён или прерван перезапуском, сохраняет уже проделанную работу. Эти строки — механизм под репликой, а не сообщения: переписка показывает вопросы и ответы, а остальное свёрнуто в след под ними. Реплика, так и не дошедшая до ответа, сообщает об этом и предлагает продолжить. Поиск и «Спросить ИИ» хранят, как и раньше, один вопрос и один ответ.
- Один прогон за раз на чат исследования. Второй вопрос, заданный, пока первый ещё выполняется, отклоняется, а не вклинивается в сохранённый разговор.
- Учётная запись может хранить 500 чатов. Сверх этого новые отклоняются, пока какие-то не будут удалены; ничего не удаляется автоматически.

Удаление документа удаляет его чаты «Спросить ИИ», а удаление учётной записи удаляет все её чаты. У коллекций `chat_sessions` и `chat_messages` нет правил API, поэтому — как и `passkey_credentials` — они вообще недоступны через `/api/collections`, и `/api/app/chats` — единственный способ до них добраться. Это сделано намеренно: клиент, способный записывать собственные сообщения `assistant`, мог бы подложить текст, который сервер затем воспроизвёл бы модели как настоящий предыдущий ответ.

## Устранение неполадок {#troubleshooting}

- **Застряли в мастере настройки, OCR не работает, извлечение ИИ не работает:** см. [AI-провайдеры → Устранение неполадок](/ru/ai_providers#troubleshooting).
- **Загрузка проходит успешно, но документ остаётся в ожидании:** убедитесь, что бэкенд-сервер запущен; воркер стартует вместе с `serve`.
- **Нет страницы «Настройки»:** войдите с email администратора (учётная запись, созданная при настройке или через `superuser upsert`). Обычные пользователи без прав администратора «Настройки» не видят.
- **Ошибки аутентификации во фронтенде:** удалите каталог данных PocketBase (`backend/pb_data`) и перезапустите, чтобы коллекции создались заново, затем перезагрузите приложение. Это также удаляет индекс Bleve (он перестраивается при следующей загрузке).
- **Поиск не находит документ:** дождитесь окончания обработки и повторите. Администраторы могут использовать **Обслуживание → Перестроить поисковый индекс** или удалить `backend/pb_data/bleve` и перезапустить.
