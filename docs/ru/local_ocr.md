# Локальное OCR {#local-ocr}

Все остальные OCR-провайдеры, с которыми работает Lemmary, читают ваши документы на чужом
оборудовании. Этот — нет: второй контейнер рядом с приложением, в той же
сети Docker, без опубликованного порта и без API-ключа. Сканы никогда не покидают
хост.

В этом и состоит всё преимущество, и стоит честно сказать о цене: образы
большие, первый документ обрабатывается медленно, а на страницу уходят секунды, а не
миллисекунды. Если ваш архив не содержит конфиденциальных данных и вы готовы платить
облачному провайдеру, [Mistral](/ru/ai_providers) быстрее и проще в эксплуатации.

## Один контейнер, несколько движков {#one-container-several-engines}

SDK называется `docling`, а контейнер —
[docling-serve](https://github.com/docling-project/docling-serve): публичный
образ на GHCR, который читает PDF, изображения, DOCX, PPTX, XLSX и HTML и возвращает
markdown с разметкой и таблицами.

Отдельного SDK для PaddleOCR намеренно нет, потому что PaddleOCR у вас уже есть.
Движок распознавания Docling по умолчанию — RapidOCR, а это собственные модели PP-OCR
от PaddleOCR, экспортированные в ONNX: свежий контейнер скачивает
`ch_PP-OCRv4_det_mobile.onnx` и `ch_PP-OCRv4_rec_mobile.onnx` и распознаёт с их
помощью. Второй многогигабайтный контейнер для тех же моделей ничего бы
не дал, а собственные образы PaddleOCR для сервинга публикуются только в реестре Baidu.
Если нужен другой распознаватель, меняйте движок, а не
контейнер: см. [Выбор движка](#choosing-an-engine).

## Запуск {#bringing-it-up}

```bash
docker compose -f docker-compose.yml -f docker-compose.local-ocr.yml up -d
```

Оба сервиса находятся за профилем compose, поэтому в команде нужно указать один из них.
Иначе `up` скачал бы оба многогигабайтных образа тому, кому нужен
был всего один движок.

Затем две строки в `.env`:

```bash
OCR_SDK=docling
OCR_BASE_URL=http://docling:5001
```

`OCR_BASE_URL` необязателен — это значение используется по умолчанию для `OCR_SDK=docling`,
поскольку это имя сервиса, которое overlay-файл даёт контейнеру. Задавайте его, только если
вы перенесли сайдкар в другое место.

`OCR_API_KEY` намеренно нет. Эти SDK работают без ключа: адрес — это
вся конфигурация, поэтому сайдкар не публикует порт и
доступен только из контейнера приложения. Если вы открываете к нему доступ шире, запустите
docling-serve с `DOCLING_SERVE_API_KEY` и укажите то же значение в
`OCR_API_KEY` — оно отправляется как `X-Api-Key`.

На экземпляре, который уже запускался, `.env` не подходит: блок ИИ
заполняет базу данных только при **первом** запуске. Вместо этого добавьте провайдер в
**Настройки → Провайдеры** (базовый URL заполнен заранее, а поля для API-ключа
нет), затем привяжите его в **Настройки → Модели → OCR**.

## Во что это обходится {#what-it-costs}

Измерено на хосте amd64 с 10 ядрами, с overlay-файлом в поставляемом виде. Ваши
цифры будут другими, но общая картина — нет.

**Диск.** Образ для CPU после скачивания на amd64 занимает 7,1 ГБ (на arm64 — меньше).
При первом запуске он скачивает около 1,3 ГБ весов моделей в именованный том;
без этого тома он скачивал бы их заново для каждого нового контейнера.

**Память.** Docling стабилизировался на **1,1 ГБ** резидентной памяти при `mem_limit` overlay-файла
в 4 ГБ — запас нужен для больших документов, а не для простоя. При
[шифровании хранимых данных](/ru/encryption) это *сверх* tmpfs, в котором находится
расшифрованный архив, так что хоста, которому раньше хватало 3 ГБ, будет недостаточно.

**Запуск.** Около **90 секунд** на холодном томе, почти всё — скачивание моделей;
**10 секунд** на тёплом. Именно это покрывает `start_period: 180s` в overlay-файле,
и поэтому том не является необязательным.

**Время на документ.** На этом хосте одностраничный PDF с исходным текстовым слоем занял **2 с**,
а одностраничный скан с разрешением 150 dpi — **4 с**, против десятков миллисекунд у облачного
API. Реальные сканы плотнее тестового образца, поэтому считайте эти цифры нижней границей и
измерьте свои.

**Настройка, о которой забывают.** `OCR_TIMEOUT_SEC` по умолчанию равен 90 секундам. Этого
хватает на несколько страниц на быстром хосте и почти ни на что больше: плотный многостраничный
документ, загруженная машина или первый запрос после перезапуска — всё это
превысит предел:

```bash
OCR_TIMEOUT_SEC=300
WORKER_TIMEOUT_SEC=1800
```

Обе переменные **применяются только при первом запуске**. На экземпляре, который уже работал,
переменные игнорируются, и значения меняются в **Настройках**.
Это самая частая причина того, что исправно работающий сайдкар даёт документы с ошибкой обработки.

У сайдкара есть собственный соответствующий предел: docling-serve прекращает
синхронное преобразование через `DOCLING_SERVE_MAX_SYNC_WAIT` секунд независимо от
того, что запросил клиент. Overlay-файл устанавливает его в 900. Держите его выше
`OCR_TIMEOUT_SEC`.

**Практический предел по страницам задаёт тайм-аут воркера, а не ограничение на число страниц.**
Lemmary отклоняет документы длиннее 1000 страниц — это ограничение пришло от Mistral. Даже
при четырёх секундах на страницу локальному движку на такой документ нужно больше часа,
что далеко за пределами любого разумного `WORKER_TIMEOUT_SEC`. Определите своё число секунд на страницу
по первым нескольким документам и подберите тайм-аут исходя из него.

**Параллелизм.** Приложение намеренно отправляет локальному движку по одной странице за раз.
Детектор разделения обычно читает четыре страницы параллельно, что скрывает сетевую
задержку облачного провайдера; с сайдкаром, делящим процессоры этого хоста, это
лишь создавало бы очередь, пока тайм-аут каждой страницы истекал бы в ожидании ядра. Поэтому
определение разделения 40-страничного документа занимает примерно в сорок раз больше времени, чем одна страница, последовательно. Дайте ему время.

## Выбор движка {#choosing-an-engine}

Привяжите **Модель OCR** в **Настройки → Модели**, чтобы сменить то, что работает внутри
сайдкара. Это необязательно — пустое значение использует движок контейнера по умолчанию, и для большинства установок
это правильный выбор. Для этого SDK поле задаёт OCR-движок, а не
модель:

| значение | примечания |
| --- | --- |
| *(пусто)* | движок контейнера по умолчанию |
| `rapidocr` | по умолчанию: модели PP-OCR от PaddleOCR в формате ONNX |
| `easyocr` | широкий охват языков |
| `tesseract`, `tesserocr` | классика; самый быстрый, но слабее всех на неаккуратных сканах |

Lemmary отправляет это значение в поле формы docling `ocr_engine`. Закреплённый образ
принимает и его, и его преемника `ocr_preset`, а `ocr_engine` помечает как
устаревшее — оно по-прежнему передаётся дальше, так что те же значения продолжают работать и после обновления
образа, пока его не удалят.

**Нераспознанное имя принимается молча.** Поле — произвольная
строка, а не перечисление: привязка `tesserract` возвращает HTTP 200, откатывается на
движок по умолчанию и ни о чём не сообщает. Если привязанный движок, похоже, ничего не
меняет, сверьте написание с таблицей выше — больше вам никто об этом
не скажет.

## GPU {#gpu}

Docling публикует образы с CUDA: `docling-serve-cu128` и `docling-serve-cu130`.
Замените строку `image:` в overlay-файле, добавьте блок `deploy.resources.reservations.devices`
для GPU, и время на страницу сократится на порядок. Приложение
менять не нужно — это тот же HTTP API.

На Mac с Apple Silicon у Docker нет доступа к GPU; вместо этого запускайте docling
нативно, как описано в разделе [Локальные OCR и эмбеддинги на Mac](/ru/local_ai_macos).

## Устранение неполадок {#troubleshooting}

- **Документы завершаются с ошибкой по тайм-ауту.** Увеличьте `OCR_TIMEOUT_SEC` в **Настройках**,
  а не в `.env`, если только это не первый запуск. См. [Во что это обходится](#what-it-costs).
- **Первый документ после перезапуска завершается ошибкой, следующие проходят.** Модели
  ещё загружались. Проверьте, что именованный том подключён — `docker compose config`
  его покажет, — и дайте контейнеру несколько минут после `up`.
- **`connection refused` с упоминанием `docling`.** Сайдкар не запущен или
  запущен без своего профиля. `docker compose ps` должен его показывать; команде
  нужен `--profile docling`.
- **`HTTP 401: Unauthorized`.** Сайдкар запущен с
  `DOCLING_SERVE_API_KEY`, но у провайдера нет ключа. Укажите то же значение в
  `OCR_API_KEY` или в поле API-ключа провайдера в **Настройках**.
- **TXT, CSV, DOCX и XLSX никогда не доходят до сайдкара.** Lemmary разбирает их
  сам, поэтому проблема с одним из них — не проблема OCR.
- **Проверьте, прежде чем доверять.** Страница **Проверка OCR** прогоняет один файл через
  провайдер, не затрагивая конвейер. Локальный сайдкар появляется там, как только
  его добавят в **Провайдеры**, ещё до привязки к OCR.

## Чего не покрывает шифрование {#one-thing-encryption-does-not-cover}

При `VAULT_ENABLED=1` архив на диске хранится в виде шифротекста, а расшифрованная копия
находится только в tmpfs. Документ, отправляемый сайдкару, передаётся открытым текстом по
сети compose, а собственное рабочее пространство сайдкара хранилищем
не защищено. Это гораздо меньший риск, чем загрузка в облачный API, — документ
никогда не покидает хост, — но он не нулевой. См.
[Шифрование хранимых данных](/ru/encryption).
