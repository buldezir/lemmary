# Локальные эмбеддинги {#local-embeddings}

Плотный (векторный) поиск — единственная ИИ-задача в Lemmary, которой не нужна передовая
модель. Модель на 500 МБ – 2 ГБ на вашем собственном CPU вполне конкурирует с
`text-embedding-3-small`, и, в отличие от OCR или извлечения данных, она обрабатывает каждый фрагмент
каждого вашего документа — так что облачный провайдер означает отправку всего
архива наружу и повторную отправку каждый раз, когда вы редактируете название или меняете
модель.

Собственный запуск полностью убирает счёт за токены и плату за каждый документ.
Не убирает он саму работу: те же прямые проходы выполняются на вашем
оборудовании, и первоначальное заполнение большого архива — единственный момент, когда это
заметно медленно. В установившемся режиме — несколько документов за загрузку — нагрузка
спокойно укладывается в пару ядер. Полную картину затрат в обоих случаях
см. в разделе [во что обходятся эмбеддинги](/ru/ai_providers#what-embeddings-cost).

SDK называется `local`: любой OpenAI-совместимый эндпоинт `/v1/embeddings`, который вы запускаете
сами. Он вычисляет эмбеддинги и больше ничего — как `AI_SDK` и `OCR_SDK` он отклоняется, —
и, как и [docling](/ru/local_ocr), не принимает API-ключ, потому что сервису в
частной сети не перед кем аутентифицироваться. Его адрес — это вся его
конфигурация.

Для Mac с Apple Silicon см. [Локальные OCR и эмбеддинги на Mac](/ru/local_ai_macos):
llama.cpp на GPU Mac вместо контейнера на CPU.

## Запуск {#bringing-it-up}

Два overlay-файла compose запускают [text-embeddings-inference][tei] как сайдкар,
и ничего в базовом файле не меняется.

Они не совсем близнецы, поэтому проверьте, какой из них вы используете:

| | CPU (`docker-compose.embeddings.yml`) | GPU (`docker-compose.embeddings-gpu.yml`) |
| --- | --- | --- |
| Привязывает приложение к сайдкару | нет — блок `app` закомментирован | да, все три переменные |
| Опубликованный порт | `127.0.0.1:8999` для отладки | нет; доступен только в сети compose |

С GPU overlay-файлом на новом томе это вся конфигурация: экземпляр
запускается с уже привязанным провайдером **Local embeddings**. С CPU overlay-файлом
три переменные задаёте вы сами — раскомментируйте блок `app` в
файле или укажите их в `.env`:

```bash
AI_EMBEDDING_SDK=local
AI_EMBEDDING_BASE_URL=http://embeddings:80/v1
AI_EMBEDDING_MODEL=BAAI/bge-m3
```

Опубликованный порт CPU overlay-файла намеренно привязан к loopback. У TEI нет
аутентификации — в этом и смысл сервиса, к которому ничто за пределами сети compose
не может обратиться, — поэтому голый `8999:80` привязался бы к `0.0.0.0` и выставил бы
в локальную сеть API инференса без аутентификации. Lemmary этот порт не использует; он
нужен для `curl 127.0.0.1:8999/info`, пока вы настраиваете модель, и
эту строку можно удалить.

Ни один из образов не мультиархитектурный. Теги `cpu-*` — это `linux/amd64`, и
`cpu-arm64-1.9` не существует — линейка arm64 публикуется без версии как
`cpu-arm64-latest`. На хосте arm64 замените тег и смиритесь с тем, что он не
закреплён.

[tei]: https://github.com/huggingface/text-embeddings-inference

```bash
# CPU, runs anywhere
docker compose -f docker-compose.yml -f docker-compose.embeddings.yml up

# NVIDIA GPU -- instead of the CPU file, not alongside it. Pick the image tag
# for your card; the file lists them.
docker compose -f docker-compose.yml -f docker-compose.embeddings-gpu.yml up
```

Оба сочетаются с [шифрованием хранимых данных](/ru/encryption), которое затрагивает только
сервис `app`:

```bash
docker compose -f docker-compose.yml \
               -f docker-compose.encrypted.yml \
               -f docker-compose.embeddings.yml up
```

В любом случае **Настройки → Модели** затем показывают ту единственную модель, которую обслуживает
сайдкар.

## Выбор модели {#choosing-a-model}

`EMBEDDINGS_MODEL` задаёт её один раз — и для сайдкара, и для привязки.

| Модель | Размерность | Окно | Веса | |
| --- | --- | --- | --- | --- |
| `BAAI/bge-m3` (по умолчанию) | 1024 | 8192 токена | ~2,2 ГБ | Хорошо работает с многими языками, и в этом весь смысл: поиск через границы языков в одном запросе — именно то, что даёт плотный поиск. Медленная на слабом CPU. |
| `intfloat/multilingual-e5-small` | 384 | 512 токенов | ~470 МБ | Быстрая, и индексу нужна вчетверо меньше оперативной памяти. Поиск слабее, а наши фрагменты длиной ~1100 символов близки к её пределу усечения. |

Обе занимают меньше места, чем облачная модель с 1536 измерениями, что особенно важно
при `VAULT_ENABLED=1`, когда индекс находится в tmpfs. Подойдёт всё, что
поддерживает text-embeddings-inference; эти две — края диапазона, с которых стоит
начинать.

Сайдкар запускается с `--auto-truncate` и `--max-client-batch-size=64` —
это размер пакета, который отправляет Lemmary. Сторонний эндпоинт, оставленный со значением TEI
по умолчанию 32, отвечает `413` на полный пакет, и документ завершается явной ошибкой,
а не повторной попыткой.

`--max-batch-tokens` — отдельный рычаг, и именно он определяет, сколько
памяти нужно сайдкару. Это бюджет TEI на прямой проход, а не ограничение размера запроса,
и на CPU он определяет большую часть резидентной памяти. Overlay-файл поставляется со значением **6144**,
выбранным под самый длинный ввод, который может отправить Lemmary: один фрагмент ограничен
8000 рун, что составляет 5723 токена в самой плотной из измеренных письменностей. Ниже этого
значения TEI молча усекает ввод — при 4096 ввод из 5723 токенов даёт эмбеддинг,
побайтно идентичный эмбеддингу его первых 4096 токенов, с кодом `200` и без предупреждения.

Рассчитывайте память хоста соответственно, потому что её превышение приводит к убийству процесса OOM во время
прогрева, а не к аккуратной ошибке. Измерено для `bge-m3` на CPU:

| `--max-batch-tokens` | Пиковая резидентная память | |
| --- | --- | --- |
| 8192 | — | Совпадает с собственным окном модели, так что ничего никогда не усекается. Требует больше оперативной памяти, чем свободно на хосте с 16 ГБ. |
| **6144** | **~8,1 ГБ** | По умолчанию. Покрывает предел ввода в 8000 рун во всех проверенных письменностях. |
| 4096 | ~6,5 ГБ | Помещается на хосте поменьше, но молча усекает плотные фрагменты. |

Overlay-файл также задаёт `mem_limit: 10g`. Прогрев до него даже не приближается; он
нужен для того, чтобы при превышении был убит сайдкар, а не что-то другое, работающее на хосте,
поскольку собственный OOM killer ядра выбирает по размеру, а не по
важности. Падение сайдкара — мягкий сбой: документы сохраняют свой текст,
метаданные и место в поиске по ключевым словам, а попытки повторяются с
нарастающей задержкой. На хосте с меньшим запасом памяти переходите на модель поменьше, а не
опускайте `--max-batch-tokens` ниже порога усечения.

## Смена модели {#changing-the-model}

Векторы двух моделей нельзя сравнивать, поэтому смена модели означает повторное вычисление эмбеддингов
для всего архива — а на экземпляре с самостоятельным хостингом для этого нужно **два** шага, потому что
вне `AI_MANAGED=1` окружение заполняет базу данных только при первом запуске:

1. Измените `EMBEDDINGS_MODEL` и пересоздайте сайдкар.
2. Измените модель и в **Настройки → Модели**.

Если сделать только первый шаг, привязка будет указывать старую модель, а сайдкар —
обслуживать новую. Это обнаруживается, а не остаётся незаметной ошибкой: приложение запоминает
длину вектора из первого ответа провайдера и отклоняет последующее
расхождение, — но архив перестаёт получать эмбеддинги, пока привязка не будет исправлена.
Изменение в Настройках сбрасывает запомненную размерность и перестраивает индекс
фрагментов, что и требуется при смене модели. При `AI_MANAGED=1`
окружение является источником истины при каждом запуске, поэтому достаточно шага 1.
