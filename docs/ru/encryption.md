# Шифрование хранимых данных {#encryption-at-rest}

По умолчанию выключено в любой сборке. Задайте `VAULT_ENABLED=1`, и на постоянном
томе будет храниться только шифротекст.

## Конфигурация {#configuration}

Всё это переменные окружения, которые читаются до того, как появляется PocketBase:
переключатель, сохранённый в `app_settings`, жил бы внутри той самой базы данных,
которую он должен защищать, и его нельзя было бы прочитать до расшифровки этой базы.
Все они есть в закомментированном блоке в `.env.example`.

| Переменная | По умолчанию | Значение |
| --- | --- | --- |
| `VAULT_ENABLED` | не задана (выкл.) | Задайте `1`, чтобы шифровать каталог данных при хранении. Тогда экземпляр запускается **заблокированным** и ждёт входа. |
| `VAULT_DIR` | `pb_data` | Где находится зашифрованное хранилище (постоянный том). |
| `VAULT_WORKDIR` | `pb_work` рядом с `VAULT_DIR` | Куда расшифровывается архив. Должна быть файловая система в памяти (tmpfs), иначе запуск завершается ошибкой. |
| `VAULT_PASSPHRASE` | не задана | Разблокирует без веб-формы — для подкоманд CLI и тестов. Сервер обычно так запускать не следует: парольная фраза лежит рядом с шифротекстом, который она защищает. |
| `VAULT_ALLOW_DISK_WORKDIR` | не задана | Разрешает рабочий каталог не в памяти **или такой, который нельзя проверить**: проверка типа файловой системы есть только в Linux, поэтому без этой переменной вне Linux вообще не запуститься. Только для разработки — это означает открытый текст на диске. |
| `VAULT_ALLOW_SHRINK` | не задана | Разрешает сброс на диск, который отбросил бы больше половины архива. |
| `VAULT_ALLOW_INSECURE_GATE` | не задана | Разрешает отдавать форму разблокировки на адресе, доступном не только с этого хоста. Только если вы согласны передавать пароль архива открытым текстом. |
| `VAULT_KEEP_GENERATIONS` | `3` | Сколько поколений сохраняется, то есть как далеко назад может дотянуться откат. |

Каждый переключатель `VAULT_*` выше — строгий булев флаг: `1`/`true`/`yes`/`on` или
`0`/`false`/`no`/`off`, а при любом другом значении запуск отклоняется, а не
угадывается. Если бы `VAULT_ENABLED=Y` читалось как «выключено», запустилась бы
установка, которую вы считали зашифрованной, и том заполнялся бы открытым текстом,
пока ни одна из гарантий ниже не действует, — поэтому это ошибка, а не значение по
умолчанию.

Обратная ошибка тоже отлавливается: запуск **без** `VAULT_ENABLED` на томе, где
лежит хранилище, отклоняется. Иначе PocketBase не нашёл бы там базы данных, создал
бы новую и показал бы свежий мастер настройки рядом с шифротекстом — архив, который
словно потерял все документы, и база данных в открытом виде, записанная теперь на
том, где должен был лежать только шифротекст. Для этого достаточно забыть
`-f docker-compose.encrypted.yml`, поэтому запуск громко завершается ошибкой.


С `VAULT_ENABLED=1` постоянный том содержит только шифротекст: базы данных SQLite и
каждый загруженный документ и превью. Украденный диск, утёкший снимок тома,
`docker cp` из остановленного контейнера или оператор, просматривающий файловую
систему, не дают ничего. Полнотекстового индекса на томе нет ни в каком виде: это
производные данные, поэтому при каждой разблокировке он перестраивается в рабочем
каталоге в памяти, а не шифруется и не хранится, — так открытая копия OCR-текста
каждого документа вообще не попадает на диск.

Векторы фрагментов Deep Research разделены так же. Сами векторы лежат в `data.db`,
поэтому на томе они зашифрованы, как любая другая строка, и попадают в снимки
хранилища и в резервные копии PocketBase без каких-либо дополнительных шагов.
Построенный по ним векторный индекс — производные данные, как и текстовый индекс:
он перестраивается в рабочем каталоге при каждой разблокировке из сохранённых
векторов, без единого запроса к провайдеру эмбеддингов, — поэтому разблокировка
ничего не стоит и работает, даже когда провайдер недоступен.

**Прочитайте весь этот раздел, прежде чем включать шифрование.** Оно меняет то, как
запускается экземпляр, что происходит при потере пароля и какие функции доступны.

## Как это работает {#how-it-works}

На томе лежат связка ключей, цепочка запечатанных манифестов и контентно-адресуемое
хранилище зашифрованных блобов — и больше ничего. При запуске экземпляр
**заблокирован**: он отдаёт страницу разблокировки и отвечает `423` на каждый
маршрут API. Первый вход предоставляет учётные данные, которые разворачивают
мастер-ключ, архив расшифровывается в рабочий каталог в памяти, и PocketBase
направляется туда. С этого момента и до остановки экземпляр ведёт себя в точности
как незашифрованная установка.

Изменения сбрасываются обратно на том примерно через десять секунд после последней
записи, по ежеминутному cron и при завершении работы.

Мастер-ключ запечатывается отдельно для каждых учётных данных, поэтому
**разблокировать экземпляр может любой его пользователь**: пароль каждой учётной
записи регистрируется автоматически при её создании или смене пароля, вместе с кодом
восстановления. Шифрование действует на весь экземпляр: после разблокировки все
пользователи видят все данные, в точности как и сейчас. Для SaaS изоляция
достигается тем, что каждый клиент получает собственный контейнер и том.

## Что оно защищает, а что нет {#what-it-protects-and-what-it-does-not}

Оно защищает от офлайн-доступа к тому: кражи или потери диска, утёкшего снимка,
резервной копии, скопированной с хоста, списанного накопителя.

Оно **не** защищает от того, кто управляет запущенным процессом. После
разблокировки ключ находится в памяти, и тот, кто запускает бинарный файл, может
изменить его так, чтобы перехватить ключ при разблокировке. Это шифрование хранимых
данных, а не zero-knowledge, и описывать его как последнее не следует. Сквозное
шифрование несовместимо с этим продуктом: OCR отправляет документы в Google Vision
или Mistral, извлечение, чат и поисковый агент отправляют OCR-текст в LLM, а
полнотекстовому поиску и SQL-фильтрам нужен открытый текст на сервере.

Также вне этой границы: логи контейнеров на хосте остаются в открытом виде.

**Отзыв учётной записи не всегда отзывает её ключ к архиву.** Том разблокирует
связка ключей, и она по необходимости отделена от настроек входа: её нужно уметь
прочитать до того, как появится PocketBase, потому что коллекция пользователей,
к которой она иначе обратилась бы, находится внутри базы данных, ещё ждущей
расшифровки. Два следствия, о которых оператор должен знать, поскольку ни одно из
них не видно в интерфейсе администратора:

- Отключение аутентификации по паролю останавливает `POST /api/token`, Basic auth
  и маршруты входа PocketBase. Оно **не** мешает тем же паролям разблокировать архив
  на загрузочном шлюзе, который эту настройку не видит.
- Удаление пользователя обычно удаляет вместе с ним и его обёртку ключа. Удаление
  **последней** оставшейся учётной записи — нет: связка ключей отказывается удалять
  свои единственные учётные данные, так как это уничтожило бы архив. Поэтому пароль
  последнего администратора, которого вывели из системы, по-прежнему расшифровывает
  том.

Там, где это важно, выполните ротацию: разблокируйте, зарегистрируйте учётные данные,
которые собираетесь оставить, и удалите учётную запись, чей ключ должен перестать
работать, пока остаётся другая учётная запись.

И сам том не непрозрачен. Хранилище блобов показывает, сколько файлов содержит
экземпляр, размер каждого из них в открытом виде (AEAD сохраняет длину) и —
поскольку адреса содержимого детерминированы в пределах хранилища — одинаковы ли
два блоба в разных снимках. Это неотъемлемое свойство контентно-адресуемого
хранилища, и парольная фраза его не меняет.

## Держите порт закрытым, пока хранилище не инициализировано {#keep-the-port-private-until-the-vault-is-initialised}

Неинициализированное хранилище задаёт мастер-пароль по первому дошедшему до него
запросу и выдаёт этому посетителю код восстановления. Пока не выполнен `vault init`
или вы сами не задали пароль, экземпляр принадлежит тому, кто первым достучится до
порта.

Публикуйте его на loopback за прокси, терминирующим TLS, — именно так делает
`docker-compose.encrypted.yml`, — или выполните `vault init` при развёртывании,
чтобы такого окна не было вовсе. По обычному HTTP в локальной сети проверки
same-origin на шлюзе не останавливают DNS rebinding, так что «в этой сети больше
никого нет» — не такая гарантия, какой кажется.

## Включение на установке, где уже есть данные {#enabling-it-on-an-install-that-already-has-data}

Это невозможно. Запуск отказывается инициализировать хранилище в каталоге, где уже
есть незашифрованная установка, потому что тогда работа началась бы с пустого
архива, а настоящие документы остались бы рядом в открытом виде.

Мигрируйте осознанно: поднимите зашифрованный экземпляр с **пустым** `VAULT_DIR` на
**новом** томе, заново импортируйте документы, затем уничтожьте старый том. Удалить
старые файлы на месте недостаточно: их содержимое остаётся восстановимым из
свободного пространства, а это ни в каком полезном смысле не шифрование хранимых
данных.

## Потеря доступа {#losing-access}

Потеря всех паролей **и** кода восстановления означает потерю архива. Обхода для
оператора нет — так задумано.

Код, сгенерированный при первой загрузке, возвращается один раз в браузер, который
инициализировал хранилище. Он намеренно **не** пишется в лог: логи контейнеров
оказываются незашифрованными на том же диске хоста, от доступа к которому защищает
эта функция, а обёртку ключа для восстановления потом нельзя отозвать.

## Неинтерактивное создание хранилища {#creating-a-vault-non-interactively}

`lemmary vault init` создаёт связку ключей для совершенно нового экземпляра и
является единственным способом получить код восстановления, если хранилище не было
инициализировано из браузера:

```bash
VAULT_ENABLED=1 VAULT_PASSPHRASE='...' lemmary vault init
```

| Результат | Код выхода | Вывод |
| --- | --- | --- |
| Хранилище создано | 0 | `vault-recovery-code: <code>` в stdout |
| Связка ключей уже существует | 0 | `vault: already initialised` в stdout |
| Всё остальное | 1 | причина в stderr |

Повторный запуск безопасен, поэтому шаг развёртывания может повторять попытки без
особого случая «а вдруг сработало». Команда **не** инициализирует PocketBase — ни
миграций, ни базы данных, ни bleve, — и это сделано намеренно: ничто не должно
иметь возможности добраться до неинициализированного мастера настройки в тот самый
момент, когда свежий архив разблокирован, а учётных записей в нём нет.

Указанный здесь пароль запечатывает **начальные учётные данные**, и они
автоматически отзываются, как только регистрируется первая настоящая учётная
запись. Это важно, потому что пароль попадает в экземпляр через то, что его
развёртывало, — его память и окружение контейнера, которое может просмотреть любой
с доступом к сокету демона, — поэтому он не должен оставаться действующим ключом к
архиву на всё время жизни экземпляра. На практике: используйте собственный пароль
учётной записи в качестве `VAULT_PASSPHRASE`, создайте учётную запись в том же
прогоне развёртывания и сразу запишите код восстановления. После этого экземпляр
разблокируется только паролями учётных записей.

Оставить `VAULT_PASSPHRASE` заданной и после этого безвредно. Когда начальная
обёртка отозвана, парольная фраза больше ничего не открывает, и вместо того чтобы
прерывать запуск — что зациклило бы перезапуски контейнера, — сервер пишет в лог,
что парольная фраза не подошла, и, как обычно, отдаёт форму разблокировки. Убрать её
из окружения всё же аккуратнее.

## Отдача страницы разблокировки по TLS {#serving-the-unlock-page-over-tls}

Форма разблокировки передаёт пароль, расшифровывающий весь архив, поэтому её нельзя
отдавать открытым текстом. Терминируйте TLS перед приложением и привяжите его к
локальному адресу:

```bash
lemmary serve --http 127.0.0.1:8090   # behind nginx/Caddy/Traefik
```

Шлюз, отдающий эту форму, работает *до* появления PocketBase, поэтому говорит по
обычному HTTP, и у него нет конфигурации TLS, на которую можно опереться. Поэтому
привязка к адресу **loopback** — единственная конфигурация, безопасность которой он
может проверить сам:

- `serve --http 127.0.0.1:8090` — разрешено. Доступно только через прокси на этом
  хосте, где и место TLS.
- `serve yourdomain.com` (встроенный autocert PocketBase) — отклоняется. В этом
  режиме PocketBase отдаёт HTTPS на `:443`, а `:80` использует только для
  перенаправления, но пока экземпляр заблокирован, на `:443` никто не слушает, так
  что у браузера, пришедшего на `:80`, нет TLS, к которому можно перейти.
- любой другой адрес, кроме loopback, включая `--http 0.0.0.0:8090`, — отклоняется,
  если не задано `VAULT_ALLOW_INSECURE_GATE=1`.

**В контейнере последний случай неизбежен и сам по себе не является проблемой.**
Внутри контейнера приложение должно привязываться к `0.0.0.0`, иначе Docker вообще
не смог бы опубликовать порт, а изнутри оно не может отличить порт, опубликованный
на `127.0.0.1`, от опубликованного на всю локальную сеть — это решается в
compose-файле. Поэтому там это и указывается: `docker-compose.encrypted.yml`
публикует порт только на `127.0.0.1` *и* задаёт `VAULT_ALLOW_INSECURE_GATE=1`,
сообщая, что это сделано. Эти две строки неразделимы. **Если вы расширяете это
сопоставление портов, уберите флаг**, иначе пароль архива пойдёт открытым текстом
туда, куда теперь доходит порт.

Отлавливается конфигурация, в которой нет ни того, ни другого: включение блока
`VAULT_*` из `.env.example` с базовым `docker-compose.yml`, который публикует порт
на всех интерфейсах хоста. Раньше такая конфигурация запускалась и отдавала форму
разблокировки всей локальной сети, потому что явный `--http` был исключён из
проверки на том основании, что его выбрал оператор, — а это исключало и штатную
точку входа, то есть каждую установку в контейнере. Теперь запуск отклоняется с
объяснением, что делать.

## Требования и ограничения {#requirements-and-limits}

- `VAULT_WORKDIR` **должен** находиться в файловой системе в памяти. Иначе
  приложение отказывается запускаться, потому что расшифровка на диск свела бы на
  нет всю функцию. Задайте размер tmpfs больше архива с запасом на рендеринг
  страниц PDF, а лимит памяти контейнера держите с хорошим запасом выше размера
  tmpfs. См. `docker-compose.encrypted.yml`.
- **tmpfs может уходить в своп, поэтому контейнеру нельзя разрешать своп.** При
  нехватке памяти ядро выгрузит tmpfs — расшифрованный архив — на устройство
  подкачки хоста, а это постоянный диск. `docker-compose.encrypted.yml` задаёт
  `memswap_limit` равным `mem_limit`, что полностью запрещает контейнеру своп;
  сохраняйте эту пару, если меняете любое из чисел. Изнутри контейнера приложение
  это обнаружить не может. Связанная вещь, тоже вне его поля зрения: **гибернация**
  хоста записывает на диск всю оперативную память, включая tmpfs, — не переводите в
  гибернацию хост, на котором работают разблокированные экземпляры.
- Пока экземпляр разблокирован, весь архив находится в оперативной памяти, поэтому
  её объём ограничивает, насколько большим может вырасти экземпляр. **Эмбеддинги
  увеличивают его дважды**: один раз за счёт векторов, хранящихся в `data.db`, и ещё
  раз за счёт построенного по ним векторного индекса в `bleve/chunks`. Закладывайте
  примерно `chunks x dimensions x 4 bytes` на каждое, плюс текст фрагментов, который
  индекс хранит для цитирования: модель с 1536 измерениями на архиве из 10 000
  документов примерно по 5 фрагментов в каждом — это около 300 МБ векторов плюс
  индекс сопоставимого размера, то есть полгигабайта tmpfs, которые экземпляру без
  эмбеддингов не нужны. Модель с 1024 измерениями или меньше обходится
  пропорционально дешевле, и поэтому здесь стоит предпочесть её, даже когда точность
  более крупной модели ничего бы не стоила. Задайте размер tmpfs в
  `docker-compose.encrypted.yml` соответственно, прежде чем включать
  `AI_EMBEDDING_MODEL`, и см. [AI-провайдеры](/ru/ai_providers#what-embeddings-cost).
- [Модель эмбеддингов, которую вы запускаете сами](/ru/local_embeddings), расходует
  оперативную память во *втором*, отдельном месте: в собственном контейнере
  сайдкара, ~2,2 ГБ весов для модели по умолчанию `BAAI/bge-m3`. Эта память
  находится вне `mem_limit` контейнера `app` и вне tmpfs, поэтому она добавляется к
  бюджету хоста, а не конкурирует с хранилищем, — но это та же оперативная память, и
  у хоста, рассчитанного ровно на зашифрованный экземпляр, свободной для неё нет.
  Выбор модели также определяет число измерений, о котором говорилось выше, и
  именно здесь локальная модель с 1024 или 384 измерениями окупается дважды.
- Векторный индекс не стоит ни одного вызова API. Как и текстовый индекс, это
  производные данные, перестраиваемые внутри хранилища из векторов в `data.db`, —
  поэтому разблокировка, восстановление или очищенный рабочий каталог стоят
  перестройки, но никогда не повторного прохода через провайдера эмбеддингов. Сами
  векторы при хранении зашифрованы, потому что лежат в `data.db`, как и всё
  остальное.
- **Хранилищем может одновременно пользоваться только один процесс.**
  `superuser upsert`, `migrate` и другие подкоманды CLI нельзя запускать при
  работающем сервере: каждый процесс расшифрует собственную копию, и последний
  сбросивший данные молча победит. Сначала остановите сервер или используйте
  интерфейс администратора. Подкоманды CLI разблокируют хранилище из
  `VAULT_PASSPHRASE`.
- Жёсткое завершение (`kill -9`, OOM, отключение питания) теряет записи с момента
  последнего сброса — секунды, а не архив. Штатная остановка ничего не теряет, если
  `stop_grace_period` достаточно велик для сброса при завершении: по `SIGTERM`
  сервер останавливает планировщик заданий, до 20 с ждёт завершения выполняющихся
  запросов и заданий воркера и только потом запечатывает архив, — так что запрос, на
  который уже ответили `200`, в нём есть. Если ожидание истекает, сервер сообщает об
  этом в логе и всё равно выполняет сброс, поскольку зависание до того, как Docker
  перейдёт к `SIGKILL`, потеряло бы строго больше.
- Собственные резервные копии PocketBase и хранилище S3 при включённом шифровании
  отклоняются: и то и другое записывало бы незашифрованные копии вне хранилища.
  Каталог хранилища сам по себе является согласованной зашифрованной резервной
  копией — копируйте его.

## Эксплуатация {#operating-it}

```bash
# Status, including generation, entry count and pending writes.
curl -H "Authorization: $TOKEN" localhost:8090/api/vault/status

# Force a flush before stopping (superuser).
curl -X POST -H "Authorization: $TOKEN" localhost:8090/api/vault/flush

# Mint another recovery code; shown once.
curl -X POST -H "Authorization: $TOKEN" localhost:8090/api/vault/recovery-code
```

Чтобы убедиться, что открытый текст не попадает на том:

```bash
docker compose stop
docker run --rm -v lemmary_app_data:/v alpine sh -c \
  'grep -rl "SQLite format 3" /v; grep -rl "%PDF-" /v' | wc -l   # must print 0
```

## Как это подключается {#how-it-attaches}

Всё подключение — это `backend/internal/boot/vault.go`: он отвечает на `vault
init` через `Result.Handled`, открывает хранилище через `vault.Open`, направляет
`Result.DataDir` на расшифрованный рабочий каталог и передаёт `v.Close` в
`Result.Close` для сброса при завершении работы.

`backend/main.go` ничего об этом не знает. Он знает лишь, что что-то может
понадобиться выполнить до создания приложения, — и в этом всё назначение
`internal/boot`: шифрование хранимых данных — единственная функция, которую нельзя
подключить к уже работающему приложению, как все остальные.
